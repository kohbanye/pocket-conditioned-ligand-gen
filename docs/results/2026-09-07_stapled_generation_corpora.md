**fullft でベースラインの方が文書数が多い。** ProLIT の `_full` は生ポーズ
23.3M から 17.2M docs に減っている (26% を記述子抽出と長さ打ち切りで失う) のに対し、
貼り合わせ側の損失は ConfSeq の 10.8% だけ。**コーパス規模の交絡は Table 3 から
消え、しかも消え方がベースラインに有利**である。

トークン数が少ないのは ESM3 が残基単位だから (1 文書 112 対 229 トークン)。
表現の性質でありハンデではないので、両方の数字を併記する。

## val 比は 3.45%、目標 3.50%

構築中に 0.12% に見えて「val 分割が壊れている」と読みかけたが、
**val ポケットのペアはシャードに強く偏在している** (shard 0 は 0.0000、
shard 3 は 0.1019、34 シャード中 22 が 0.005 未満)。ビルドはシャード順に
進むので、序盤に val がほとんど出ないのは分布どおりだった。
分割をやり直して「直して」いたら、2 つのコーパスが静かに食い違っていた。

p5–p7 はノード待ちで 35 分遅れて開始した 3 本。**潰した仮説**:

- **データの偏り**: パーティションは `pair_idx % 8` で切れる。8 スライスとも
  件数が完全同一 (316,661)、`_min` 比率 0.2351–0.2373、`label==1` 比率
  0.1981–0.1998。**化学的に同一**。
- **コード変更**: 関連ファイルの最終更新は両バッチ投入前 (前日 17:35)。
- **メモリ**: RSS 194–215 GB、OOM 無し。
- **タスク欠落**: 全 8 本が 280/280、合計 2,240 = 35 shards × 64 slices で網羅。
  ポーズ数も各 2.91M で均一。

**壊れてはいない。** マージ後のコーパスから head/middle/tail 各 400 文書を
抽出して検査したところ **1200/1200 が整形式** (BOS/P_OPEN で始まり
L_CLOSE/EOS で終わり、最大 id 12738 < 12740)、索引とストリームもトークン単位で
一致。失われたのは**書かれなかった約 110 万文書**であって、壊れた文書ではない。

損失はベースラインに不利な方向だが、それでも 20.8M > ProLIT の 17.2M なので
学習は止めない。原因は引き続き調査する。
