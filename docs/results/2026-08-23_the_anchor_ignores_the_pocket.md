## 数字

正準フレームはポケットの CA 原子から作られるので、リガンドは構造上その
原点付近にいる。ならば**ポケットを一切見ず、「全標的のリガンド重心の
平均」を答えるだけの予測器**がどれだけ当たるのかを測った (正典 100 標的)。

| | 誤差 中央 (A) |
|---|---|
| **ポケットを見ない定数予測 (全標的の平均)** | **2.14** |
| **CLM のアンカー誤差 (正しいポケット)** | **2.13** |
| CLM のアンカー誤差 (別標的のポケット) | 3.02 |
| CLM のアンカー誤差 (ポケット無し) | 3.54 |
| 原点 (0,0,0) を答える | 2.30 |

**同一。** CLM の最初の原子の配置は、ポケットを一度も見ない定数予測器と
統計的に区別がつかない。

## これで全部つながる

これまでの否定的結果が、すべて同じ一つの事実の帰結だった:

| 観測 | 説明 |
|---|---|
| 別標的のポケットでも 0.65 -> 1.04 A しか悪化しない | 元々使っていない。誤ったポケットは積極的に誤誘導するので、無いより悪い |
| classifier-free guidance が単調に悪化する | 増幅すべきポケット信号が無い。(cond - uncond) はほぼノイズ |
| ポケットの並び順 (distord) に相関が無い (+0.056) | 読んでいないものの順番は効かない |
| 生成分子が参照から 2.1 A ずれる | アンカーが 2.13 A ずれ、分子はその周りに整合的に組み上がる |
| ずれの 79% がばらつき | 定数予測の周りをサンプリングしているだけ |
| near-native fine-tune でアンカーが悪化 (2.25 -> 3.39) | ポケットではなく周辺分布を学んでいるので、分布が変わると壊れる |

## なぜ学習が失敗するか

1. **フレームが答えを半分渡している。** 正準フレームはポケット由来なので、
   周辺分布の平均を答えるだけで 2.14 A に届く。ポケットを読む勾配圧力が弱い。
2. **アンカーは損失の 1/25。** 損失は全リガンド原子の平均で、最初の原子は
   その 1 つ。下流は全部これを継承するのに、重みは他と同じ。
3. ポケットブロックは約 400 トークン、リガンドは約 25 トークン。

## 打ち手

`--anchor-loss-weight` / `--anchor-loss-atoms` を実装
(`ProLITCLMModule.forward` の重み付き分岐)。既存の経路は
`weight == 1.0` でそのまま通り、重み付き経路も weight≈1 で
**9.5e-07 の差**で一致することを確認済み (数値等価)。

w = 10 / 30 を掃引中 (job clmanch、gpu_1 パイロット 8000 step)。

判定は val loss ではなく**アンカー誤差そのもの**で行う。2.13 A が
2.14 A (ポケット非依存の下限) を明確に下回れば、初めて条件付けが
機能したことになる。

## 効かなかった打ち手の一覧 (すべてこの発見の前に潰した)

自己回帰ドリフト / 誤差のカスケード / decoy 除去 / near-native fine-tune /
正準原子順 / 幾何による選別 (衝突・PB・ポケット重心) / 制約付きデコード /
記述子の自己整合性 / MLM による修復 / 腐敗学習した修復器 /
ポケットの並び順 / classifier-free guidance (学習前・学習後とも)

効いたもの: リファイナ (-0.87 kcal/mol)、rescorer 選別 (+0.43)、
アンカー温度 (幾何で -16%、Vina 測定中)。

## 打ち手 1: アンカー損失の重み付け -- 効かない (8000 step パイロット)

`--anchor-loss-weight 10 / 30`、先頭 3 リガンドトークン、
`clm_e250lig3_fullft` から fine-tune:

| | アンカー誤差 中央 | 平均 | 完全一致 | 全原子 中央 |
|---|---|---|---|---|
| 現行 CLM | 2.253 | **2.226** | 0.013 | **1.150** |
| w=10 | 2.053 | 2.371 | 0.013 | 1.179 |
| w=30 | **2.003** | 2.393 | 0.013 | 1.184 |
| ポケット非依存の下限 | 2.140 | | | |

中央値はわずかに下がるが**平均は悪化**し、対応差は **p=0.40 / 0.42**。
完全一致は 0.013 のまま動かない。全原子の誤差はむしろ悪化。

**損失を重くしても、ポケットを読む「能力」は与えられない。**
周辺分布によく当てはまるだけ。約 400 個の離散トークンから
「どこに空洞があるか」を計算するのは、transformer にとって重い。

## 打ち手 2: フレームの原点を変える -- 支持されない

原点がリガンドの居場所に近ければ、下限そのものが下がる。候補を測った:

| 原点の定義 | リガンド重心までの距離 中央 (A) |
|---|---|
| ポケット残基の CA 重心 (現行) | 2.30 |
| ポケット全重原子の重心 | 2.14 |
| 最も空いた格子点 (空洞中心) | 21.36 |
| 最も空いた 8 点の平均 | 15.69 |

重原子重心にしても 2.30 -> 2.14 で、ほとんど変わらない。

空洞中心が 21 A なのは**実装が素朴だから**で、ポケットの
バウンディングボックス内で最も空いた点は、ポケットの中ではなく
タンパク質の外側に来る。本格的な空洞検出 (格子を protein に囲まれた
領域に制限する) なら違う結果になりうるが、この確認では支持されない。

フレーム変更はトークン列のバイト表現を変え**全 checkpoint を無効化する**
ので、この程度の見込みでは払えない。

## 情報はトークンに入っている (トークナイザは無罪)

LM が見るのはポケットの生座標ではなくトークン列。復号して座標に戻したときの
誤差が、LM が空洞を特定できる精度の上限になる (60 標的):

| | 座標誤差 |
|---|---|
| 全ポケット原子 RMSD | **0.321 A** |
| 原子ごとの最大 | 0.886 A |
| **空洞を囲む原子 (リガンド 5 A 以内)** | **0.269 A** |
| (参考) リガンド側の往復 | 0.350 A |
| **(参考) CLM のアンカー誤差** | **2.13 A** |

**LM は 0.27 A の精度でポケット幾何にアクセスできている。** それでアンカーを
2.13 A 外す。**情報は存在し、正確で、使われていない。**

## 対照実験: 学習なしの幾何式でも 2.13 A を破れる

「そもそも当てられないなら、モデルを責められない」という可能性を潰す。
学習を一切しない幾何予測器を並べた (70 標的):

| 予測器 (学習なし) | 誤差中央 (A) |
|---|---|
| **凹面重み付き重心** | **1.83** |
| ポケット非依存の定数 | 2.14 |
| **CLM (正しいポケット)** | **2.13** |
| ポケット原子の重心 | 2.26 |
| Chebyshev 中心 | 2.35 |
| 埋没度上位の重心 | 6.07 |
| 囲まれた最も空いた格子点 | 12.98 |

凹面重み付き重心 = 各ポケット原子を「周囲 8 A の受容体原子数」の逆数で
重み付けした重心。**1 行の式**で 1.83 A。

**ポケットには取り出せる配置信号があり、素朴な幾何でも見つかる。
298M パラメータの言語モデルがそれを使っていない。**

## 診断の完成形

| | |
|---|---|
| ポケットのトークン化精度 | 0.27 A (空洞を囲む原子) |
| 学習なしの幾何式で到達可能 | 1.83 A |
| ポケット非依存の定数予測 | 2.14 A |
| **CLM の実測** | **2.13 A** |

CLM は定数予測の水準にいて、素朴な幾何式にすら負けている。
情報不足でも、課題が不可能でもない。**モデルが条件を使っていない。**

打ち手として損失の重み付け (p=0.40)、CFG (悪化)、コーパスの入れ替え
(悪化)、ポケットの並び替え (相関なし) をすべて潰した。残るのは
**アーキテクチャ側で条件付けを強制すること** (ポケットからリガンド重心を
直接回帰する補助ヘッド等) か、**推論時に幾何式の答えを使って選別・制約する
こと**。後者を `concave_centre_selection.py` で測定中。

## 打ち手 3: 補助ヘッドで条件付けを強制する

最初のリガンドトークンは `<l>` 位置の隠れ状態から予測される。その状態に
ポケット由来の位置情報が乗っていないのが問題なら、**その量を直接出させれば
よい**。損失の重み付け (「もっと頑張れ」) が効かなかった (p=0.40) のは、
勾配を増やしてもポケットからその状態への経路が生まれないため。

`--centroid-loss-weight` を実装 (`ProLITCLMModule._centroid_loss`)。
`<l>` 位置の隠れ状態から 2 層 MLP でリガンド重心を回帰する。

**既存の重みを壊さない**: ヘッドは `self.model` の外に置くので、
これ無しで学習した checkpoint はそのまま読める。

**コーパスを作り直さない**: 教師信号の座標は
`pipelines/corpora/code_mean_coords.py` が作る「コードごとの平均復号座標」の
表 (7924/8192 コードを観測) から、文書のリガンドコードを平均して求める。
デコーダは文脈依存なのでコード単体の座標は定義できないが、**平均は定義でき、
25 原子で平均すれば十分**。

### 教師信号の精度 (投げる前に確認した)

| | 誤差中央 (A) |
|---|---|
| **コード平均表から求めた重心** | **0.779** |
| 学習なしの幾何式 | 1.83 |
| CLM のアンカー誤差 | 2.13 |

0.779 A は目標水準より十分小さく、教師信号として使える。
**これを確かめずに投げていたら、効かなかったときに「補助ヘッドが
悪いのか教師信号が悪いのか」が分からなかった。**

重み 1.0 / 5.0 を掃引中 (job clmcen)。判定は val loss ではなく
**アンカー誤差**で行う。2.13 A が 1.83 A (幾何式) を下回れば、
初めて「モデルがポケットを使った」と言える。

## 表現には答えが入っている。使っていないのは出力側だった

補助ヘッド自身が重心を予測できるようになったかを測った (70 標的):

| | 誤差中央 (A) |
|---|---|
| **補助ヘッド (w=5.0) の重心予測** | **0.584** |
| 補助ヘッド (w=1.0) | 0.603 |
| 教師信号自体のノイズ床 | 0.78 |
| 学習なしの幾何式 | 1.83 |
| **同じモデルの LM ヘッドが置くアンカー** | **2.35** |

**`<l>` 位置の隠れ状態には、リガンドの居場所が 0.6 A の精度で入っている。**
2 層 MLP で取り出せる。それなのに**同じ隠れ状態を読む LM ヘッドは
2.35 A 外す**。

### 診断の最終形

| 段階 | 精度 |
|---|---|
| ポケットはトークンに入っているか | **0.27 A** ○ |
| その位置は `<l>` 隠れ状態に抽出されているか | **0.60 A** ○ |
| **トークン予測はそれを使っているか** | **2.13-2.35 A** ✗ |

**エンコーダでも表現でもなく、最終的なトークン予測が使っていない。**
softmax は 8192 コードの周辺分布に収束していて、lr 5e-5 の
2000-4000 step では経路が付け替わらない (しかもアンカーはトークン損失の
1/25)。

これは「アンカー損失の重み付けが効かなかった (p=0.40)」とも整合する:
勾配を増やしても、既に収束した softmax を動かすには足りない。

### 補助ヘッド (centroid) 自体は却下

生成には効かなかった:

| | アンカー中央 | 改善標的 | p |
|---|---|---|---|
| 現行 CLM | 2.253 | - | - |
| w=5.0 (2k step) | 1.850 | 51% | 0.57 |
| **w=5.0 (4k step)** | **2.348** | 51% | 0.39 |
| w=1.0 (4k step) | 2.111 | 50% | 0.90 |

2k の 1.850 は揺らぎで、4k では基準を上回るところまで戻る。
**中央値だけ見て報告していたら誤った結論になっていた。**

### 次の 2 手 (どちらもこの発見から直接出る)

1. **教師信号を最初の原子にする** (`--centroid-target anchor`)。
   重心を 0.6 A で当てても、最初の原子は重心から中央 1.98 A 離れているので
   アンカーには効かない。**この見落としが centroid 版が効かなかった
   理由の一部**。学習中 (job clmanc2)。
2. **アンカーだけ softmax に任せない**。ヘッドの予測位置から遠いコードを
   最初のトークンから除外する。`code_mean_coords` の表があるので
   推論時にできる。1 が当たれば直接つながる。


## 訂正後の診断: 問題は原子順だった

| 予測対象 | 定数予測の誤差 (= 予測可能性の下限) |
|---|---|
| リガンド重心 | 2.14 A |
| **最初の原子 (file 順)** | **3.24 A** |
| **最初の原子 (buried_first 順)** | **1.28 A** |

最初の原子が重心からどれだけ離れているか: file 順 2.19 A、
buried_first 順 1.96 A (ほぼ同じ)。効いているのは距離ではなく
**どの原子が選ばれるかの一貫性**。

### これで全部つながる (今度は正しく)

- **CLM のアンカー 2.13 A は、file 順の下限 3.24 A を 1.1 A 上回る。**
  ポケットは使われている。
- **補助ヘッドが最初の原子を 3.35 A でしか当てられなかったのは、
  ヘッドが悪いのではなく量が予測不能だから。** file 順の下限 3.24 A と
  ほぼ一致する。
- **重心なら 0.58 A で当てられる。** 隠れ状態は「分子がどこに行くか」を
  正確に知っている。知らないのは「その最初の原子がどれか」。
- **アンカー損失の重み付けが効かなかった (p=0.40) のも同じ理由。**
  教師信号自体が本質的に不確実なので、重みを増やしても学べない。

### 打ち手は原子順

`buried_first` はポケット重心に最も近い原子から始めるので、最初の原子が
**正準な幾何量**になる。下限が 3.24 -> 1.28 A に下がる。

これは「SDF が既に連結順なので直せるのは 5.5% の原子だけ」という
以前の評価より**はるかに強い根拠**。連結性の話ではなく、
**アンカーが予測可能になるかどうかの話**だった。

`vq_e250_ord` (epoch 99, val/atom_coord 0.1051、基準は epoch 244 で 0.1022)
が学習済み。次は
`descriptor_cache_allatom_ord` -> トークン化 -> CLM 学習 -> 生成 -> 評価。

### buried_first にはコストもある

`vq_e250_ord` (epoch 248, val/atom_coord 0.1051) の往復精度を A で測ると、
基準より**悪い**:

| | RMSD 中央 (A) | 平均 | p90 |
|---|---|---|---|
| 基準 (file 順, epoch 244) | **0.365** | 0.392 | 0.531 |
| ord (buried_first, epoch 248) | 0.459 | 0.485 | 0.700 |

26% 悪い。原子順が変わればデコーダの仕事も変わるので、驚くことではない。

**差し引きの見積り**:

| | 効果 |
|---|---|
| アンカーの予測可能性の下限 3.24 -> 1.28 A | +0.6 kcal/mol 程度 (期待) |
| 量子化誤差 0.365 -> 0.459 A | -0.3 kcal/mol 程度 |

**プラスだが劇的ではない。** 測る価値はあるが、これで FLOWR との
4 kcal/mol が埋まるとは考えにくい。

`val/atom_coord` (0.1051 vs 0.1022) は正規化空間の値で、A の差
(0.459 vs 0.365) より小さく見える。**この指標だけで判断しないこと。**

### 原子順アブレーションの規模をそろえる (踏んだ罠)

最初のトークン化は訓練文書 **17,778** しか出なかった。基準の `_full` は
**16,528,675**。1000 倍近い差で、この規模で CLM を学習しても
「原子順の効果」ではなく「過学習の度合い」を測ることになる。

原因は 2 つ:

1. `--pocket-split` の既定 `--max-per-pocket 32`。
2. **キャッシュが違う。** 基準の `_full` は
   `descriptor_cache_atom_full` (**28,228,531 件**、全ポーズ) から作られている。
   `descriptor_cache_allatom_ord` は良ポーズのみの **351,006 件**。

| キャッシュ | 件数 |
|---|---|
| `descriptor_cache_full` | 37,915,660 |
| **`descriptor_cache_atom_full`** | **28,228,531** |
| `descriptor_cache_allatom` (file 順、良ポーズ) | 351,006 |
| `descriptor_cache_allatom_ord` (buried_first) | 351,006 |

`buried_first` を 28M 規模で作るには記述子生成からやり直しになる。

**代わりに規模をそろえたアブレーションにする**: 両方の順序を 351k
キャッシュから**同一設定**でトークン化し、同じように学習する。
配備モデルとは規模が違うが、**原子順の効果だけは切り出せる**。

`--max-per-pocket 100000` (実質無制限) で `lm_tokens_abl_ord` /
`lm_tokens_abl_file` を作成中。

**注意**: 順序を変えると VQ も変わる (往復 0.365 vs 0.459 A) ので、
このアブレーションは「順序 + そのトークナイザ」の効果であって、
順序だけを分離したものではない。分離は原理的にできない。
