# 和集合の val は 60% 汚染されていた (2026-09-13)

事前登録と訂正: `docs/notes/2026-09-13_affinity_prereg.md` の H7。
**この文書の数字は H7 の判定に使えない。** clean 版の再実行待ち。

## 何が起きたか

BioLIP Kd/Ki と PDBbind v2020 Kd/Ki を足した和集合コーパスで、val は BioLIP 側を
バイト単位で流用した (両腕が同一の 431 文書で早期終了するように)。
しかし **PDBbind は BioLIP のタンパク質群 val 分割を知らずにトークン化されている**ので、
**BioLIP の val 432 pdb のうち 258 (59.7%) が PDBbind 側の学習データに入った**。

投入前のメモにはこう書いてあった: 「PDBbind の学習側を BioLIP の val タンパク質で
濾していないので、この腕の val は checkpoint 選択の分だけ楽観的」。
**「分だけ」で済む量ではなかった。**

| | rot1 (BioLIP のみ) | union (汚染) |
|---|---|---|
| 最良 val loss | 0.81〜0.85 | **0.48〜0.52** |
| 最良 epoch | 1〜4 | **9〜10** |

## どう気づいたか、そして最初の検査はなぜ足りなかったか

val loss の落ち方が大きすぎた。最初に**トークン列の完全一致**で leak を探したが
**0 件**だった。これは検査として厳しすぎる: 同じ PDB でも BioLIP の
receptor/ligand ファイルと PDBbind の protein.pdb/ligand.sdf では、ポケットの
切り出しも原子順も座標も違うので、**トークン列は一致しない**。
pdb id の水準で照合し直して確定した。

**教訓**: 2 つのコーパスを足すとき「片方の val が他方の train に入っていないか」は
**必ず id 水準**で確かめる。トークン列やハッシュの一致では見つからない。

## 汚染下での数字 (記録のみ、判定には使わない)

CASF 自体は汚染されていない (両コーパスとも `eval_holdout_pdbs.txt` を除外)。
つまり以下は**正しい測定**だが、**選ばれた checkpoint が汚染された val で選ばれている**。

| | seed 7 | seed 11 | seed 12 | 平均 ± sd |
|---|---|---|---|---|
| union R | 0.8079 | 0.8015 | 0.8122 | **0.8072 ± 0.0054** |
| rot1 R | 0.7957 | 0.7694 | 0.6981 | 0.7544 ± 0.0505 |
| union ρ | 0.6579 | 0.6702 | 0.6667 | **0.6649 ± 0.0064** |
| rot1 ρ | 0.7175 | 0.7228 | 0.6456 | 0.6953 ± 0.0431 |

対にすると R は 3/3 で union が上 (平均 +0.053)、ρ は 2/3 で union が下。

## 一番気になるのは平均でなく分散

**union の seed 分散が 8 倍小さい** (R sd 0.0054 対 0.0505、ρ sd 0.0064 対 0.0431)。
事前登録で「独立なラベルを増やすのは平均を上げる手であり分散を下げる手でもある」と
書いた通りの形ではある。もし clean 版でも残るなら、
**[[feedback_single_run_comparisons]] の「腕あたり 3 seed」というコストが下がる**ので、
平均が上がるかどうかとは別に価値がある。

**ただしこれ自体が leak の産物かもしれない**: 汚染された val はどの seed でも同じ
遅い epoch を選ばせるので、それだけで 3 本が似た解に揃う。clean 版が分ける。

## 次

を除外して PDBbind を再トークン化 (job 8657668) → 和集合を作り直して 3 seed。

出しており、残しておくと後から誰かが最良値として拾うため。
