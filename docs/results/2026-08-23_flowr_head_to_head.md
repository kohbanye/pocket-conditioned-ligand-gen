# FLOWR を自分で走らせて比べる (2026-08-23)

論文値を引くのをやめ、FLOWR を同じ 100 ポケット・同じ receptor pdbqt・
同じ Vina 設定・同じ PoseBusters 設定で走らせた。理由は単純で、FLOWR の論文は
Vina Score しか報告しておらず、この表が並べる 3 つのうち 2 つが無いから。

70 標的が揃った時点の集計 (残りは走行中)。

## 数字

**標的ごとの中央値の、中央値**で取る。平均は使えない — FLOWR は 4 標的で
Vina が発散 (+46 〜 +155 kcal/mol) し、標的平均がそれだけで壊れる。
実際、最初に平均で集計して FLOWR の score を -1.50 と書きかけた。

**94 標的** (生成 99、評価済 94。残りは走行中):

| | ProLIT | FLOWR | 差 | ProLIT が勝つ標的 | p |
|---|---|---|---|---|---|
| **Vina Score** | -1.90 | **-5.73** | +4.02 | 6% | 8.5e-12 |
| **Vina Min** | -4.43 | **-6.04** | +1.56 | 18% | 3.6e-09 |
| **Vina Dock** | -6.95 | **-7.31** | +0.18 | 42% | **0.020** |

| | PB | clash-free | 分子 |
|---|---|---|---|
| ProLIT | 0.928 | **0.970** | 9400 |
| FLOWR | **0.951** | 0.883 | 7988 |

**3 つとも FLOWR が上。** ただし大きさが桁違いに違う: score で 4.02、
min で 1.56 に対し、**dock は 0.18 で、標的の 42% では我々が勝つ**。
dock は我々のポーズを一切使わないので、**分子としてはほぼ互角、
わずかに FLOWR が上**。負けの本体は置き場所。

> **訂正**: 70 標的の時点で dock を「有意差なし (p=0.063)」と書いたが、
> 94 標的では p=0.020 で FLOWR が有意に上。差 0.18 kcal/mol は小さいが、
> 「互角」ではなく「わずかに負け」が正しい。

## 公平性について

固定したもの: テストポケット、参照リガンド、receptor pdbqt、Vina の設定と
探索ボックス、PoseBusters の設定、1 標的あたりの要求サンプル数 (100)。

固定していないもの: **学習データ**。FLOWR は SPINDR、ProLIT は
CrossDocked2020。これは実在する差で、表のキャプションに書くべきもので、
「両方ここで走らせた」ことで消えるものではない。

FLOWR 側に当てたパッチ 2 件はどちらも生成内容を変えない:
- PyMOL のライセンス探索が `/opt/schrodinger` を無条件に stat してコアダンプ
  (`third_party/patches/pymol_licence_probe.py`)
- 生成物が RDKit mol にならなかったとき、多様性フィルタが None で例外を投げる
  (`third_party/patches/flowr_none_ligands.patch`)。落とした個数は出力する。

論文値との照合: 論文 score -6.29 / PB 0.92、ここでの実測 -5.61 / PB 0.956。
**評価器がやや辛い**が、順位は変わらない。

## 天井の再解釈 (前の note の訂正)

`2026-08-23_tokenizer_ceiling.md` で「トークナイザ天井 -5.86 は FLOWR の
-6.29 に届かない」と書いたのは**誤り**。-5.86 は我々の評価器の値、-6.29 は
FLOWR 論文の値で、比べられない。同一評価器で FLOWR は **-5.61**。

| | score (同一評価器) |
|---|---|
| 参照分子・結晶ポーズ | -6.61 |
| 参照分子・VQ 往復 + refiner = **天井** | **-5.86** |
| **FLOWR (実測)** | **-5.61** |
| 我々の分子が到達しうる上限 (= その dock) | -6.90 |
| ProLIT (実測) | -1.72 |

**トークナイザは FLOWR 越えを妨げていない。** 天井 -5.86 は FLOWR の
-5.61 より上で、我々の分子自身の上限 -6.90 はさらに上。

**残っている差は全て言語モデルの置き場所。** score で 4.14 kcal/mol の
余地があり、FLOWR はその途中にいる。

## どの標的で負けるか

Vina が発散した標的を除いた 93 標的で、score の差 (正 = 我々が負け) と
何が相関するか:

| | Spearman | p |
|---|---|---|
| **FLOWR の dock** | **-0.807** | 0.000 |
| **FLOWR の分子サイズ** | **+0.642** | 0.000 |
| 我々の分子サイズ | +0.450 | 0.000 |
| 我々の衝突数 | +0.422 | 0.000 |
| 我々の dock | -0.466 | 0.000 |
| FLOWR の衝突数 | -0.109 | 0.298 |

**大きく親和性の高い分子が作れる標的ほど、大きく負ける。** FLOWR は
そこでちゃんと作り、かつ置けている。93 標的中、我々が勝つのは 5 標的だけ
(そこでは我々の分子が 29 原子と大きく、衝突も少ない)。

これは以前の「ポーズ損失は分子サイズと相関する (+0.673)」と同じ現象を
対戦相手側から見たもの。置き場所の誤差は大きい分子ほど高くつく。

## 参照リガンドのサイズは使っていない

`scripts/generate_ligands_for_target.py` には `--min-atoms-frac` があり、
参照リガンドの重原子数に比例した最小長を課せる。**比較に使った生成では
無効** (`SBDD_OWN_MIN_ATOMS_FRAC` 既定 0、ジョブスクリプトにも設定なし)。
分子サイズは LM が自分で決めている (中央 24 原子、FLOWR 21 原子)。

FLOWR 側は `--sample_mol_sizes` で自前の分布からサイズを引く。どちらも
参照のサイズを直接は見ていない。ただし**両方とも参照リガンドの位置で
ポケットを切り出している** (FLOWR は `--ligand_file` + `--cut_pocket`、
こちらは `PocketExtractionConfig`)。これは SBDD ベンチマーク共通の前提で、
片方だけの利点ではない。

## 訓練データへの漏れ (測って、影響を出した)

生成 SMILES が参照リガンドと完全一致した標的:

| | 標的 | 完全一致 | 最大 Tanimoto 中央 | >0.8 の標的 |
|---|---|---|---|---|
| **ProLIT** | 100 | **8** | 0.204 | **12** |
| FLOWR | 99 | **0** | 0.266 | 1 |

再現した 8 標的は残りより明確にスコアが良い:

| | n | score | dock | 参照原子 |
|---|---|---|---|---|
| 再現あり | 8 | **-2.67** | **-8.30** | 22 |
| 再現なし | 91 | -1.72 | -6.96 | 21 |

11-15 原子の小分子は偶然の一致もありうるが、ABL2 (33 原子)、
KS6A3 (31)、VAOX (27) の完全一致は偶然ではない。

### 比較への影響は小さく、しかも我々に不利な方向

| | n | ProLIT | FLOWR | 差 |
|---|---|---|---|---|
| 全標的 | 98 | -1.89 | -5.63 | +3.98 |
| 完全再現を除外 | 90 | -1.75 | -5.63 | **+4.04** |
| Tanimoto>0.6 も除外 | 82 | -1.83 | -5.51 | **+4.07** |

**除外すると差はわずかに広がる。** 漏れは我々に有利に働いていたが、
除いても結論は変わらない。

### 何が漏れているのか (未確定)

`tokenize_crossdocked.py` には `--exclude-pockets data/sbdd_bench_pockets.txt`
(93 ポケット、「訓練ポーズの 2.6% を失う」) があるが、`_full` コーパスの
構築時に使われたかの記録が無い (トークン化に `run.json` が残らない)。

ポケットが除外されていたとしても、**同じリガンドが別の複合体として
CrossDocked に入っている**ことはありうる。それは SBDD ベンチマーク共通の
状況で、DiffSBDD / TargetDiff も同じ。ポケット自体が漏れているかどうかは
別問題で、**論文に出す前に確定させる必要がある**。

`--train-smiles` の仕組みは `run_evaluation.py` にあるが、訓練 SMILES の
ファイルが用意されておらず、Novelty は未測定。
