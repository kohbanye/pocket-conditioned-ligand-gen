# 生成タスクの課題整理と、有効な改善策 (2026-08-20)

97 標的の確定値は PB-valid **0.795** / Vina score median **+3.36**
(FLOWR: 0.92 / -6.29)。PB は射程内、Vina は約 10 kcal/mol 差。
Vina score が正なのは斥力項そのもの、すなわち**衝突**であり、
**生成タスクの課題は事実上「衝突」ひとつに集約される**。

---

## 1. 衝突の正体は「約 2 A の誤配置」

結晶リガンドを剛体的にずらして LM の衝突統計を再現すると:

| 剛体変位 | clash-free | 平均衝突 |
|---|---|---|
| 0 A | 0.880 | 1.20 |
| 1.34 A | 0.240 | 4.39 |
| **2.0 A** | **0.170** | **8.24** |
| **LM 実測 (refiner なし)** | **0.103-0.117** | **7.3-8.5** |

**LM は化学的にまともな分子を、約 2 A ずれた場所に置いている。** これで
- PB がそこそこ良い (分子自体は壊れていない)
- ポーズを保つ設計の局所緩和が衝突に効かない
- Vina min (局所最適化) が -4.00 止まりなのに再ドッキングが -7.00 に届く

が全て説明できる。

## 2. 犯人はデコーダではなく LM のトークン選択

encode -> decode を通したときの座標変化:

| | 変位 |
|---|---|
| 参照リガンド | 0.398 A |
| **LM 生成分子** | **0.439 A** |

ほぼ同じ。**生成分子はデコーダにとって自然な場所にいる**ので、
「デコーダの文脈依存が誤差を累積させている」という仮説は否定される。
トークン列は自己整合しており、壊しているのはデコーダではない。
選ばれたトークン列そのものが、当該ポケットに対して誤った位置を指している。

（したがって「デコーダを再設計すべき」という以前の結論は誤り。）

## 3. 化学の条件付けは効いている。効いていないのは幾何

生成分子の Tanimoto 類似度:

| | 平均 |
|---|---|
| 同一標的内 | 0.197 |
| 異なる標的間 | 0.073 |

差 +0.125 で、ポケットごとに異なる分子を出せている。つまり
**「どんな分子か」は条件付けできていて、「どこに置くか」だけができていない。**

## 4. 副因: 大きすぎる分子

| サイズ比 (生成/参照) | n | clash-free | 平均衝突 |
|---|---|---|---|
| 0.8-1.0 | 510 | 0.353 | 3.91 |
| 1.0-1.2 | 337 | 0.214 | 4.22 |
| **1.5 以上** | **311 (16%)** | **0.148** | **9.26** |

相関 r = +0.33。ただしサイズを 0.8-1.0 に揃えても clash-free は 0.353 止まりで、
結晶の 0.85 には遠い。**サイズは副因、主因は配置**。

## 有効だと考えられる改善策

### A. 位置の量子化解像度を上げる (最有力)

コードブック 8192 の**異なるコード間の位置間隔は中央値 1.456 A**
(`2026-08-19_no_clash_masking_at_decode.md` の測定)。観測された誤配置 ~2 A は
**コード 1-2 個分の選び間違い**に相当する。つまり LM が 1 つ間違えるだけで
衝突する粒度でしか位置を表現できていない。

* コードブック拡大 (8192 -> 32768) で間隔を約半分に。ただし 13 bits/atom という
  論文の主張が 15 bits になる。
* **位置と化学を別コードブックに分ける**方が筋が良い。現在は 1 コードに
  (位置・元素・電荷・混成・環・numH) を全部詰めており、位置に割ける分解能が
  化学の分だけ削られている。位置専用コードブックなら化学のビットを食わずに
  解像度を上げられ、総ビット数もほぼ据え置ける。
  ablation の `separate` とは別の分け方 (modality ではなく属性で分ける)。

### B. ポケット-リガンド相対位置の明示的な条件付け

ポケットとリガンドは同じ正準フレームを共有しているので、LM は原理的に相対位置を
知れるが、attention で暗黙に学習させている。生成長 ~250 トークンのうち
リガンドは ~24 なので、ポケット 210 トークンとの空間関係を学ぶ信号が薄い。
相対距離を明示的に与える (相対位置エンコーディング等) のは自然な補強。

ただし**モデルを複雑にする方向**なので、A を先に試すべき。

### C. 生成サイズをポケット体積に合わせる

16% がサイズ比 1.5 以上で、その群は clash-free 0.148 と突出して悪い。
ポケット体積から期待重原子数を決めて `min/max_new_tokens` を制御する。
参照リガンドのサイズを使うのはリークなので、**受容体だけから決まる量**
(ポケット候補原子が囲む体積) を使うこと。効果は clash-free +0.05 程度と
見積もられ、A ほどではないが安価。

### D. 試して失敗した手 (再挑戦しないこと)

| 手法 | 結果 |
|---|---|
| 局所緩和 (ポーズ保存) | clash に無影響。設計通り |
| pocket-aware 緩和 | PB 0.932 -> 0.851、clash はほぼ不変 |
| refiner (jitter 腐敗) | 腐敗上限 0.93 A で deployment の半分、補正不足 |
| refiner (code resample 腐敗) | 局所幾何を壊す。PB 0.858 -> 0.463 |
| refiner (剛体腐敗 2.11 A) | 推論が発散 (train 0.419 / val 2.76e7) |
| 剛体アライメント (重心合わせ) | box 中心 0.188 / ポケット重心 0.019。そのまま 0.272 より悪い |
| 受容体制約デコーディング | コードに固定位置がない (文脈で 1.383 A 動く) ため不可能 |
| LR アニール | val 5.357 -> 5.703 と悪化 |
| サンプリング温度 1.0 -> 0.6 | clash-free 0.269 -> 0.308、多様性 597 -> 537 SMILES |
| near-native コーパス化 | val 5.357 -> 3.728 と激変。**衝突は 0.117 -> 0.103 で不変** |

最後の行が重要: **データを直しても衝突は動かない**。律速はデータではなく
位置表現の粒度である、という A の根拠になっている。

## PB (0.795 -> 0.92) について

衝突ほど深刻ではない。緩和後の残存要因は

| check | 通過率 |
|---|---|
| bond_lengths | 0.864 |
| bond_angles | 0.882 |
| internal_steric_clash | 0.895 |
| all_atoms_connected | 0.934 |

UFF フォールバックで緩和成功率 78% -> 86% にしたが PB は +0.0085 しか動かず
(16 標的サンプルの +0.038 からの外挿は楽観的すぎた)。
`all_atoms_connected` 0.934 = 6.6% が分断しており、これは緩和では直らない
生成側の問題。A で位置精度が上がれば結合認識も安定するので、
**PB も A の副次効果で改善する見込み**。
