# 分析フェーズの結果と改善候補（2026-08-03）

`2026-08-01_gap_analysis_and_6week_plan.md` で設計した分析フェーズを実行した記録。
学習は一切していない。全て forward パスと既存 dump の再集計で、
「トークナイザを作り直すべきか」という一番高価な判断に必要な材料を先に揃えることを狙った。

測定は scratchpad の使い捨てスクリプトで行い、リポジトリには入れていない。
評価集合は `descriptor_cache_allatom` の shard 32–34 と、CASP16 は既存の
`benchmarks/recon-bench/results/*.parquet` の再集計。ただし**シャードは split では
ない**ことに途中で気づいたので、下の注意書きを先に読むこと。

結論を先に書くと、**トークナイザを作り直す必要は無い**という判断になった。
根拠は §4 と §7 にある。

### 測定上の注意（途中で気づいた 2 つの欠陥）

**1. シャードの先頭を取ると代表性が無い。** シャード内の項目は受容体ごとに
グループ化されて並んでいるので、先頭 N 件は数個の受容体のポーズばかりになる。
実際 shard 32 の先頭 600 件はリガンド平均 28.6 原子、シャード全体では 23.0 原子。
per-atom / per-bond の平均と対応付きの勝率はこれにほぼ影響されないが、
**「全結合が許容内に入った分子の割合」は結合数の指数なのでサイズ分布に非常に敏感**で、
同じモデルでも 0.002 から 0.27 まで動く。per-molecule の率を出す表には
母集団と平均リガンドサイズを必ず書いた。**異なる母集団の per-molecule 率を
比べてはいけない。**

**2. shard 32–34 は held-out ではない。** split は `pair_idx` を使って
manifest の fold ラベルから作られるので、シャード境界とは無関係である。
実測すると shard 32–34 は **約 68% が fold0 の train** だった。
§7 は fold0 == test かつ CASF/sbdd を除いた真の held-out で取り直してある
（n=710、平均 20.9 原子）。§1–§6 の測定は混在した集合の上にあるが、
取り直した §7 と比べて結論は変わらなかった（例: joint の生の全結合通過率は
混在 0.099 に対し test のみ 0.156、順序も比も同じ）。

### 学習データのリーク（新規に発見）

**CASF-2016 コアセットの 285 複合体のうち 169 が CrossDocked の manifest にあり、
そのうち 25,345 行が fold0 = train 側にある。** つまり公開済みの VQ-VAE
`xzkjxu9q` は、CASF のリスコアリング／親和性で評価する受容体の幾何を学習時に見ている。
下流の MLM は `nocasf` 系で除外されているが、その下のトークナイザは見ていた。

fold の test 側は DataModule が正しく除外しているので、リークは CASF と
sbdd-bench の 3 標的に限られる。除外しても学習データは 1.69% しか減らない
（good pose 303,616 行のうち 5,128 行）ので、**新しい run は必ず除外する**。
`prolit.data.holdout` と `--exclude-eval-pdbs` を入れた。

refiner の学習データ (`data/pose_refine_atom`) は 2026-07-19 作成で、
除外コードの履歴（2026-07-23 以降）より古く、**除外が入っていた確証が無い**。
meta にも記録が無い。作り直す（§9 R4）。以後は meta に `held_out` を記録する。

## 0. 前提: checkpoint のロードは解決済み

分析を始めた時点で、`8c46966` により 167 run / 493 ファイルの checkpoint が
全てロードできない状態だった。これを 2026-08-03 に解消した。

一時的な reader（`torch.load` の `pickle_module` だけを差し替える ~40 行）で
旧クラスパスの checkpoint を読み直し、現行クラスパスで保存し直した。
447 ファイル / 527 GB を移行して失敗はゼロ。1 ファイルずつ「別ファイルに書く →
plain な `torch.load` で読み直す → state_dict を全テンソル照合 → `os.replace`」
という順にしたので、検証を通るまで元ファイルには触れていない。
移行後に一時 reader は削除し、公開ローダー 6 本と recon-bench の腕 2 本が
shim 無しで通ること、`pytest` が 135 passed であることを確認した。

除外した 46 ファイル（16 run）は `cc2a95d` で `nn.Module` ごと削除された
2 世代前のトークナイザで、config を直しても使えないため触っていない。

この経験自体が記録に値する。config dataclass を改名・移動しても、
「一時 reader → 再保存 → reader 削除」という手順を踏めば重みは救える。
CLAUDE.md の「改名する = 既存の重みを捨てる」は今も真だが、退路はある。

## 1. どの段で何が失われるのか

### 1.1 記述子・連続 latent・量子化のどれが効いているか

まず、同じ held-out リガンド 395 分子を 3 通りにデコードして、同じ指標で比べた。
記述子の往復（ネットワークを通さない）、エンコーダ+デコーダだが量子化を飛ばした場合、
そして実際の VQ 往復である。量子化の寄与とデコーダ自身の限界を分けたかった。

| 段 | RMSD | Kabsch | bond MAE | angle MAE | element acc | arom acc |
|---|---|---|---|---|---|---|
| 記述子往復（ネットなし） | 0.000 | 0.000 | 0.000 | 0.00° | 1.000 | 1.000 |
| 連続 latent（量子化なし） | 0.224 | 0.204 | 0.107 | 6.69° | 0.998 | 0.999 |
| VQ 8192（実物） | 0.368 | 0.311 | 0.150 | 11.27° | 0.994 | 0.997 |
| （参考）ConfSeq @CASP16 | — | 0.721 | 0.042 | 2.68° | — | — |

記述子スキーマ自体は無損失だった。(r, θ, sin φ, cos φ) と Cartesian の変換は可逆なので
当然ではあるが、失われるものが全てネットワークと量子化に由来することがこれで確定する。

重要なのは真ん中の行で、**量子化を完全に外しても bond MAE は 0.107 Å までしか下がらない**。
ConfSeq の 0.042 Å の 2.5 倍である。codebook をどれだけ大きくしてもこの水準は越えられない、
ということになる。二乗で分解するとデコーダ由来 0.107 / 量子化由来 0.105 でほぼ半々だが、
デコーダ側だけで既に ConfSeq の 2.5 倍という点が効く。

一方で化学チャネル（元素・芳香族性など）は量子化後もほとんど劣化していない。
**失われているのは幾何だけ**、と言い切れる。

### 1.2 分子を壊しているのは LM か、トークナイザか

生成分子が 32% 断片化し、3 員環が 1 分子あたり 0.92 個も湧く（TargetDiff は 0.00）
という症状は既に分かっていたが、それが LM のせいなのかトークナイザのせいなのかは
切り分けられていなかった。同じ held-out ポケット 150 個に対して、
結晶リガンド・真のトークンをデコードしたもの・ポケットに条件付けて
ProLIT-CLM がサンプルしたトークンをデコードしたものを、同じ指標で並べた。

| | 結晶 | VQ 往復 | LM 生成 | VQ+射影 | LM+射影 |
|---|---|---|---|---|---|
| 重原子数 | 28.3 | 28.3 | 28.1 | 28.3 | 28.1 |
| sanitize | 1.000 | 0.873 | 0.813 | 0.873 | 0.787 |
| 連結（1 断片） | 1.000 | 0.500 | 0.493 | 0.613 | 0.607 |
| 断片数 | 1.000 | 1.634 | 1.615 | 1.374 | 1.263 |
| 3 員環/分子 | 0.033 | 0.520 | 0.507 | 0.533 | 0.487 |
| 非結合最近接 (Å) | 2.187 | 1.969 | 1.959 | 2.142 | 2.136 |
| 予測芳香族原子率 | 0.545 | 0.545 | 0.554 | — | — |

結果ははっきりしていて、**VQ 往復と LM 生成がほぼ同じ値になる**。
連結性 0.500 と 0.493、3 員環 0.520 と 0.507、断片数 1.634 と 1.615。
つまり LM は分子の壊れ方に何も足していない。真のトークンをそのままデコードした
時点で既に半分の分子が断片化しており、3 員環も湧いている。

**生成分子の化学的な欠陥は、LM の問題ではなくトークナイザのデコードと
その後の組み立ての問題**である。ここが今回いちばん効いた切り分けで、
LM の作り直しという高価な選択肢を消せた。

なお芳香族原子率はどの段でも 0.55 前後で結晶と一致している。
モデルは芳香族性の情報を持ったままである。これは §5.3 で効いてくる。

## 2. なぜ結合が壊れるのか

### 2.1 誤差が原子ごとに独立している

per-atom RMSD が 0.35 Å 程度なのに bond MAE が 0.16 Å もあるのは、
隣り合う原子の誤差が揃っていないからではないか、と考えて実際に測った。
結合している 2 原子の誤差ベクトルのなす角の cos を取ると、剛体的・滑らかな変形なら
1 に近づき、独立なノイズなら 0 に近づく。

| | 連続 latent | VQ 8192 |
|---|---|---|
| per-atom \|err\| | 0.215 | 0.354 |
| per-bond ΔL | 0.118 | 0.160 |
| 結合ペア間の誤差ベクトル cos | +0.341 | +0.373 |

**+0.37 だった**。ほぼ独立と言ってよい。結合長は 2 つの独立な誤差の差なので、
per-atom の誤差がそのまま結合長の誤差に乗る。

これは損失の設計を見れば予想できることでもあった。`vqvae.py:_compute_recon_loss` の
中身は per-atom の Cartesian MSE とリガンドの clash hinge だけで、
**結合長にも結合角にも項が無い**。さらに、記述子には `knn_offsets`
（K=4 の近傍相対座標）が入力として入っているのに `ATOM_RECON_HEADS` には
対応する出力ヘッドが無く、局所幾何は一度も教師されていない。
デコーダは局所幾何を合わせろと言われたことが無いので、合っていない。

### 2.2 分子単位の PB validity は per-bond 精度の指数になる

許容幅を振って、結合 1 本ごとの通過率と分子単位の全通過率を比べた。

| 許容 | per-bond 通過 | per-mol 全通過 |
|---|---|---|
| 0.15 Å | 0.595 | 0.023 |
| 0.20 Å | 0.716 | 0.089 |
| 0.25 Å | 0.798 | 0.144 |
| 0.30 Å | 0.861 | 0.218 |

per-bond が 0.80 でも分子単位では 0.144 まで落ちる。実測の CASP16 PB-valid 0.124 と
整合する。分子は結合を 25 本前後持つので、**PB-valid ≒ (per-bond 精度)^(結合数)** に
なるわけで、CASP16 のサイズ層別もそれを裏書きしている。

| リガンドサイズ | n | PB-valid | pb_bond_lengths | pb_bond_angles |
|---|---|---|---|---|
| ≤15 原子 | 29 | 0.759 | 0.759 | 0.966 |
| 16–25 | 81 | 0.123 | 0.123 | 0.432 |
| 26–40 | 180 | 0.028 | 0.033 | 0.167 |
| >40 | 8 | 0.000 | 0.000 | 0.000 |

裏を返せば、per-bond を 0.80 から 0.98 に上げられれば PB は一気に跳ねる。
指数なので、per-bond のわずかな改善が分子単位では大きく効く。

### 2.3 落ちているのは bond_lengths と bond_angles だけ

総合の PB-valid でまとめると原因が見えなくなるので、サブチェックに分解した
（CASP16, リガンド, n=303）。

| サブチェック | joint | separate 4096 | binning | ConfSeq |
|---|---|---|---|---|
| bond_lengths | 0.128 | 0.292 | 0.000 | 0.756 |
| bond_angles | 0.312 | 0.527 | 0.000 | 0.868 |
| internal_steric_clash | 0.913 | 0.889 | 0.164 | 0.988 |
| aromatic_ring_flatness | 0.886 | 0.966 | 0.715 | 1.000 |
| sanitization | 1.000 | 1.000 | 1.000 | 0.812 |
| all_atoms_connected | 1.000 | 1.000 | 1.000 | 1.000 |
| internal_energy | 0.970 | 0.960 | 0.333 | 1.000 |
| （総合）pb_valid | 0.124 | 0.275 | 0.000 | 0.594 |

落ちているのは bond_lengths (0.128) と bond_angles (0.312) の 2 つだけで、
残りは全て 0.89 以上ある。再構成では参照の結合グラフを持ち回すので
連結性や sanitize は自明に通り、失敗は純粋に幾何だと分かる。
**PB-valid 0.124 という数字は、実質「結合長が合っていない」の一言に還元できる。**

## 3. 壊れた幾何は戻るのか

ここが今回いちばん効いた測定である。デコーダが局所幾何を壊しているとして、
その情報がコードから失われているのか、それとも出力の形式のせいで散らかっているだけなのかで、
打つべき手が全く変わる。前者ならトークナイザを作り直すしかないが、後者ならデコード側で済む。

VQ 再構成の座標に真の結合グラフを付けて、MMFF の位置拘束付き最小化をかけた
（`MMFFAddPositionConstraint`、n=295）。拘束を強くすれば原子はほとんど動けないので、
「わずかに動かすだけで幾何が整うか」を見ることになる。

| 位置拘束 | bond MAE | angle MAE | per-bond<0.25Å | per-mol 全通過 | 動いた量 | Kabsch |
|---|---|---|---|---|---|---|
| なし（生の VQ 出力） | 0.156 | 11.86° | 0.806 | 0.064 | 0.000 | 0.331 |
| k=1 | 0.076 | 7.36° | 0.997 | 0.898 | 0.525 | 0.480 |
| k=5 | 0.076 | 7.14° | 0.997 | 0.898 | 0.375 | 0.334 |
| k=20 | 0.075 | 6.67° | 0.997 | 0.895 | 0.297 | 0.279 |

**原子を平均 0.30 Å 動かすだけで、分子単位の結合全通過率が 0.064 から 0.895 になった。**
しかも Kabsch RMSD が 0.331 から 0.279 へ、つまり参照座標にも近づいている。
幾何を整える方向と参照に近づく方向が一致しているということで、
これは「情報は残っていて、置き方だけが散らかっていた」ことの直接の証拠になる。

**したがってトークナイザの作り直しは要らない。** デコード側を直せば済む。
原則 7 の「1 世代の作り直しは 1 回しか回せない」を、ここでは使わなくてよい。

## 4. 共有 codebook は何を買って何を払っているか

論文の主張の核は「protein と ligand を同じ語彙で書く」ことなので、
その損得を数字で押さえておきたかった。

### 4.1 コードの取り合いを見る

まず学習データ中の原子数比を数えると **protein : ligand = 8.30 : 1** だった。
EMA codebook は量子化イベントの数だけ重心を動かすので、この比がそのまま効く可能性がある。
実際にコードの使われ方を数えた（n=3000 複合体）。

| | |
|---|---|
| protein が使うコード | 8183 / 8192 |
| ligand が使うコード | 6907 / 8192 |
| ligand 専用コード | 5 |
| 共有コード | 6902 |
| ligand 原子質量のうち「ligand が使用の 10% 未満」のコードに乗る割合 | 24.8% |

コード数だけ見れば ligand も 6907 個使えているが、**そのほぼ全てが protein との共有**で、
専用コードは 5 個しかない。そして ligand 原子の 1/4 は、ほぼ protein が重心を決めた
コードに量子化されている。

### 4.2 共有コードは実際に精度を落としているのか

上は「そうなっていそう」という状況証拠なので、誤差と突き合わせた。
held-out 1200 複合体、joint arm、リガンド原子 34,200 個。

| リガンド原子が乗るコード | per-atom 誤差 | n |
|---|---|---|
| protein と共有 | 0.356 | 32,117 |
| ligand 専用 | 0.287 | 2,083 |

**共有コードに乗ると誤差が 24% 悪化する。** そして専用コードに乗れるのは
リガンド原子のうち 6% だけである。共有のコストがそのまま数字になった。

対照として、コードの出現頻度と誤差の関係も見た。5 分位に切って 0.345〜0.358 と
完全にフラットで、**稀なコードが悪いわけではない**。codebook の利用率を上げる方向の
対策（デッドコード復活など）は効かない、ということでもある。

### 4.3 腕どうしを同じ複合体で突き合わせる

集計値の差だけでは分からないので、held-out 1200 複合体で対応付きの比較をした。

| 指標 | joint | separate 4096 | joint 勝率 | p (Wilcoxon) |
|---|---|---|---|---|
| リガンド Kabsch ↓ | 0.342 | 0.236 | 0.031 | 8.8e-194 |
| リガンド bond MAE ↓ | 0.163 | 0.086 | 0.004 | 9.1e-198 |
| protein RMSD ↓ | 0.283 | 0.377 | 0.997 | 3.0e-196 |
| lDDT-PLI ↑ | 0.988 | 0.986 | 0.550 | 1.5e-08 |
| Contact-F1 ↑ | 0.821 | 0.808 | 0.588 | 7.3e-14 |
| 界面 clash ↓ | 0.006 | 0.005 | 0.072 | 0.22 (n.s.) |

（この 1200 複合体は shard 32 の先頭から取ったもので、train/test が混在しており
リガンドも平均より大きい。per-atom / per-bond の値と勝率は影響を受けないが、
per-molecule の全結合通過率はサイズに敏感なので §7 の真の held-out の値を使うこと。
そちらでは joint 0.156 / separate 0.513。）

**joint は protein で大きく勝ち、リガンド分子内で大きく負け、界面では有意だが小さく勝つ。**
ちょうど原子数比のとおりで、8.3:1 のデータ質量が protein 側の精度に化けている。

界面指標が 0.99 近くで飽和しているのは held-out が in-distribution だからで、
腕を分離できるのは CASP16 の方（lDDT-PLI 0.931 vs 0.920、Contact-F1 0.689 vs 0.644）。

リスコアリングでは joint が大差で勝つ（CASF DP@2Å 87.4 vs 70.9）。
これが単なる学習不足でないことも確認した。pose head の val loss は
joint が 3 epoch で 0.19、separate は 9 epoch 回して 0.34 で、
**separate は長く回しても追いつかない**。共有語彙は界面タスクに効いている、
という論文の主張自体は測定に支持されている。

### 4.4 フレームの選択も同じくらい効いている

CASP16 の既存 dump を並べ直すと、負けの要因が codebook の共有だけではないことが分かる。

| 腕 | book | リガンド frame | ligand PB | bond MAE |
|---|---|---|---|---|
| joint | 8192 共有 | pocket | 0.124 | 0.184 |
| separate 4096 | 4096+4096 | pocket | 0.275 | 0.145 |
| separate | 8192+8192 | pocket | 0.419 | 0.117 |
| localframe | 8192+8192 | ligand 自前 | 0.607 | 0.093 |

book サイズを 8192 に揃えたまま、リガンドをポケットフレームで書くか自前フレームで書くかを
変えるだけで PB が 0.419 → 0.607 になる。1 bit/atom の効果は separate の
8192 → 4096（0.419 → 0.275）で約 0.14 と分かるので、フレームの効果はそれより大きい。
**ポケットフレームで絶対座標を書くこと自体が、局所幾何にとって不利**ということになる。

### 4.5 どこが苦手なのか（層別）

held-out 1200 複合体で切れるだけ切った。

protein 側は backbone より sidechain が悪い（joint で 0.220 vs 0.283）。
残基種で見ると良い順に Ala 0.173 / Pro 0.220 / Val 0.225、悪い順に
Tyr 0.334 / Arg 0.325 / Phe 0.281 で、大きく柔軟な側鎖ほど悪い。

リガンド側は元素で C 0.349 / N 0.326 / O 0.447 / S 0.522（joint）と、
ヘテロ原子ほど悪い。混成で見ると芳香族 0.302 < SP2 0.334 < **SP3 0.452**、
環内 0.334 < 環外 0.406。**剛直で予測しやすい部分ほど正確で、
自由度の高い部分ほど不正確**という、素直だが分かりやすい傾向が出ている。

結合を環サイズで切ると、非環 0.160 / 5 員環 0.175 / 6 員環 0.161 に対し
**4 員環が 0.238 と突出して悪い**（separate はそれぞれ 0.083 / 0.104 / 0.082 / 0.118）。
元素ペアでは C-N 0.148 < C-C 0.172 < C-O 0.177 < N-N 0.214 の順。

### 4.6 平均に出ない壊れ方

分位点と裾も見た（joint, n=1200）。

| 指標 | p0 | p10 | p50 | p90 | p100 |
|---|---|---|---|---|---|
| lig Kabsch | 0.214 | 0.276 | 0.335 | 0.421 | 0.621 |
| bond MAE | 0.081 | 0.127 | 0.160 | 0.206 | 0.291 |

## 5. 組み立て段（座標から分子を作るところ）

§1.2 で「壊しているのは LM ではなく VQ デコードと組み立て」と分かったので、
組み立て段そのものを測った。現状は距離しきい値による結合知覚
（`d < r_i + r_j + 0.4 Å`）で、その後は全て単結合として書き出している。

### 5.1 距離しきい値では 65% が上限

VQ デコード座標に `infer_bonds` をかけ、結晶座標から得た正解グラフと比べた（n=500）。
しきい値も振って、調整で済む話なのかを確かめた。

| tol | recall | precision | 取りこぼし/分子 | 偽陽性/分子 | グラフ完全一致 |
|---|---|---|---|---|---|
| 0.20 | 0.834 | 0.996 | 2.99 | 0.06 | 0.168 |
| 0.30 | 0.916 | 0.993 | 1.51 | 0.11 | 0.376 |
| 0.40（現行） | 0.966 | 0.985 | 0.61 | 0.26 | 0.600 |
| 0.50 | 0.984 | 0.967 | 0.28 | 0.60 | 0.650 |
| 0.60 | 0.993 | 0.929 | 0.12 | 1.37 | 0.558 |

**どのしきい値でもグラフの完全一致は 65% が上限だった。**

締めればその逆になる。しきい値はレバーではない。

### 5.2 射影を反復しても直らない

§3 で位置拘束 MMFF が効くと分かったので、正解グラフが無い状況でも
「知覚 → 射影 → 再知覚」を繰り返せば収束するのではないかと考えて試した（n=400）。

| | グラフ完全一致 | 取りこぼし | 偽陽性 | 連結 | 3 員環 |
|---|---|---|---|---|---|
| 生のデコード | 0.618 | 0.650 | 0.258 | 0.730 | 0.128 |
| 射影 1 回 | 0.672 | 0.518 | 0.272 | 0.805 | 0.132 |
| 射影 2 回 | 0.672 | 0.512 | 0.275 | 0.808 | 0.132 |
| 射影 3 回 | 0.672 | 0.510 | 0.275 | 0.808 | 0.132 |

1 回で収束してしまい、完全一致は 0.672 止まり。連結性は 0.730 → 0.808 と改善するが、
**偽陽性、つまり 3 員環はまったく減らない**（0.128 → 0.132）。
理由ははっきりしていて、誤って張られた 3 員環は力場から見れば正当なシクロプロパンなので、
最小化は喜んでそれを保存する。**最初の知覚が間違っていると後段では直せない。**

### 5.3 モデルが持っている情報が捨てられている

では何を手がかりにすればいいのか。VQ 往復後のリガンド原子について、
化学チャネルの復元精度を測った。

| チャネル | 精度 |
|---|---|
| charge | 1.0000 |
| element | 0.9956 |
| aromatic | 0.9949 |
| hybrid | 0.9868 |
| numH | 0.9835 |

### 6.1 トークンはポーズ情報を落としていない

剛体変位でポーズを動かし、リガンドトークンの変化率を測った（n=75）。

| 0.25 Å | 0.239 | 0.000 |
| 0.50 Å | 0.447 | 0.000 |

| 2.00 Å | 0.885 | 0.000 |

## 7. 決定的な実験: 幾何を直したとき腕の差は残るか

ここまでで、joint はリガンド分子内で separate に大きく負け、
protein と界面とリスコアリングでは勝つ、という構図が出た。
一方 §3 では、位置拘束付き最小化がリガンドの幾何をほぼ完全に直すことも分かっている。
そこで**両アームに同じ幾何修復をかけたら差が残るのか**を確かめた。

修復は 2 通り試した。ひとつは §3 の MMFF 射影（力場、oracle として上限を測るためだけに使う）、
もうひとつは **既存の学習済み refiner** である。後者を試したのは、
`refine_atom_bond_v1` が元々 **x0 = native リガンドの VQ 再構成 → x1 = 結晶ポーズ** の
flow matching で学習されている、つまり**再構成の幾何修復そのものを学習している**のに、
これまで生成でしか使われたことが無かったからである。

母集団は**真の held-out**（CrossDocked fold0 == test、かつ CASF / sbdd 標的を除外）
から一様抽出した n=710 複合体、リガンド平均 20.9 原子、22.1 結合/分子。

| arm | 段 | Kabsch | bond MAE | per-bond 通過 | 全結合通過 | 非結合最近接 | 動いた量 |
|---|---|---|---|---|---|---|---|
| joint | 生の VQ 出力 | 0.301 | 0.145 | 0.840 | 0.156 | 2.012 | — |
| joint | 学習 refiner ×1 | **0.253** | 0.103 | 0.945 | 0.413 | 2.055 | 0.314 |
| joint | 学習 refiner ×3 | 0.255 | 0.077 | 0.977 | **0.644** | 2.121 | 0.333 |
| joint | MMFF oracle | 0.265 | 0.072 | 0.997 | 0.946 | 2.301 | 0.285 |
| separate | 生の VQ 出力 | 0.239 | 0.090 | 0.946 | 0.513 | 2.089 | — |
| separate | 学習 refiner ×1 | 0.248 | 0.102 | 0.948 | 0.418 | 2.049 | 0.264 |
| separate | 学習 refiner ×3 | 0.254 | 0.078 | 0.977 | 0.668 | 2.113 | 0.296 |
| separate | MMFF oracle | 0.266 | 0.071 | 0.997 | 0.946 | 2.302 | 0.247 |

読み取れることが 3 つある。

**第一に、幾何を直すと腕の差は消える。** 学習 refiner を 3 回かけた後、
joint と separate は全結合通過 0.644 と 0.668、bond MAE 0.077 と 0.078、
Kabsch 0.255 と 0.254 でほぼ並ぶ。MMFF oracle でも 0.946 と 0.946 で同じ結論になる。
つまり joint の唯一の実質的な弱点だったリガンド局所幾何は、後段で消える性質のものだった。
消した後の joint は protein でも界面でもリスコアリングでも separate に勝つので、
**主系統を joint にする根拠が全指標で揃う。**

**第二に、学習 refiner だけで oracle の 6 割強まで届いている。**
このタスク向けの再学習を一切していないのに、joint の全結合通過は 0.156 → 0.644。
bond MAE に至っては 0.077 で oracle の 0.072 にほぼ並ぶ。
そして 0.644 という値は、**ConfSeq の PB-valid 0.594 を既に上回っている**
（母集団は違うので直接比較はできないが、桁は合っている）。
力場を使わずここまで来ているので、refiner を再学習すれば超えられる見込みが十分ある。

**第三に、残っている差は主に内部衝突である。**
非結合最近接は refiner が 2.121 までしか戻せないのに対し MMFF は 2.301 まで戻す。
bond MAE では並んでいるのに全結合通過で 0.644 vs 0.946 の差がつくのも、
分子ごとに残る少数の悪い結合と衝突が効いているため。
**refiner の再学習で狙うべきはここ**（clash 項の強化と反復数）だと特定できる。

なお Kabsch では **学習 refiner が MMFF oracle を上回る**（1 step で 0.253 vs 0.265）。
力場は「物理的に妥当な形」に寄せるだけだが、refiner は結晶ポーズを予測するよう
学習されているので、参照そのものに近づく。学習の道を選ぶ実質的な利点である。

## 9. 改善候補

**前提**: 力場は成果物に入れない。使ってよいのは学習した重みだけで、
VQ デコーダとその後段の学習済みリファイナまでを「モデル」とする。
§3 と §7 の MMFF は**上限を測るための oracle** としてのみ使い、論文には
「力場ならここまで戻る／学習モデルはそのうち何割を達成した」という形で残す。
この基準により、これまで生成側で使っていたポケット緩和
（`relax_in_pocket.py`、手書きの soft 反発項）も成果物から外す。

### 学習不要（数時間で通せる）

**C2. 組み立て段をモデルの化学予測で駆動する**

§5 で、距離しきい値による結合知覚はどう調整してもグラフ完全一致 65% が上限で、
射影の反復でも偽陽性が減らないことが分かった。一方でモデルは
numH 98.4% / aromatic 99.5% / charge 100% を持っている。
距離だけで結合を決めるのをやめ、**復元した element + numH + charge から
各原子の重原子次数を決め、それに整合する結合集合を距離証拠のもとで選ぶ**
（マッチング問題として解く）ようにする。そのうえで結合次数を割り当てる。
使うのはモデル自身の出力だけなので、力場を排した基準にも合致する。

期待できるのは連結 0.50 → ~1.0、3 員環の消滅、芳香環ゼロ 92% → ベースライン並み、
QED 0.38 → ~0.49（`_bo` 腕で実測済み）。**生成タスクではこれが一番大きいレバーで、
LM にも VQ にも触らない。**

**C4. 100 標的・単一モデル・既定ハイパラの主系統を 1 本作る**

F1（3 標的とベースライン 100 標的の混在）と原則 9。現状 100 標的での最良は
棄却サンプリング込みの `sep4096_cs800`（vina_dock −7.80 vs DiffSBDD −7.35, p=0.0004）だが、
これはプール 1150 からの採択なので、同一予算をベースラインにも与えた列が要る（F5）。
ポケット緩和を外す分 Vina Score の出発点は −2.6 に戻るので、
そこから C2 と R1/R3/R4 でどこまで戻せるかが生成側の勝負になる。

**C5. リスコアリングの報告値を正直な選択に差し替える**

§6.2 に従い主表は DP@2Å 90.4 / DP@1Å 76.5 とし、論文の 94.4 / 81.0 は撤回する。
ヘッド選択は検証集合で 1 回だけ行い、原則 9 に従って主系統は
mean-pool + MLP の単一ヘッドにする。

### 学習あり

**R4. リファイナを幾何修復器として再学習する（最優先・最も安い）**

§7 が示すとおり、既存の `refine_atom_bond_v1` は**このタスク向けの学習を一切
していないのに** joint の全結合通過を 0.099 → 0.596 まで戻し、bond MAE では
MMFF oracle にほぼ並ぶ。残差は内部衝突と、分子あたり数本残る悪い結合に集中している。

やること:

1. **clash 項を強める。** 非結合最近接が refiner 2.103 に対し MMFF 2.291。
   `_clash_bond_losses` の重みと距離の床を上げる。
2. **反復数を増やす。** 1 step より 3 step が明確に良い（全結合通過 0.331 → 0.596）。
   推論の既定を 3 に上げ、学習時も複数ステップを想定する。
3. **x0 の分布を広げる。** 現状 x0 は native リガンドの VQ 再構成のみ。
   ここに **LM が生成したポーズ**を混ぜる。これが同時に、外したポケット緩和の
   役割（受容体との重なり解消）を学習モデルに引き取らせる部分になる。
   refiner は既にポケット条件付きで `lp_edge` によるリガンド–ポケット clash 損失を
   持っているので、アーキテクチャの変更は要らない。
4. **再構成でも評価する。** 今まで生成でしか測っていなかった。recon-bench に
   refiner ありの腕を足す。

VQ より安く（既存の refine run は数時間規模）、**VQ の再学習を待たずに今すぐ回せる**。
そして再構成タスクのゴール（ConfSeq の PB 0.594 超え）はこれ単体で届く可能性がある。

**R1. VQ の損失に局所幾何を入れる**

§1.1 が示すとおり、量子化を外しても bond MAE 0.107 Å が下限で、これはデコーダ設計の限界である。
損失を変えない限りここは動かない。安い順に、

1. **`knn_offsets` の再構成ヘッドを足す。** 記述子に入力としてあるのに出力ヘッドが無い。
   中身は「4 近傍への変位の球座標 (Δr, θ, sin φ, cos φ)」そのものなので、
   `ATOM_RECON_HEADS` に 1 行足すだけで局所幾何が直接教師される。データ変更は不要。
2. 1-2 / 1-3 距離の損失を足す。ただし cache に結合グラフが入っていない
   （キーは protein / ligand / elements / pair_idx / pose_idx）。有機分子なら K=4 の
   KNN が結合近傍をほぼ覆うので、まず 1 で代替できるか見る。
3. clash hinge の床 1.2 Å を上げる。§4.6 のとおり 68.5% が 2.0 Å 未満なので、
   現状の床は事実上機能していない。ここは R4 の clash 項と役割が重なるので、
   どちらに持たせるかは実測で決める。
4. **デコーダに近傍相対座標を出させ、絶対座標は積み上げで決める。** これが本命かもしれない。
   §4.4 のとおり `localframe` 腕は力場も refiner も無しで bond MAE 0.093 / PB 0.607 を
   出している。違いはリガンドを自前フレームで書いているかどうかだけで、
   **絶対座標を全トークンに載せること自体が局所形状に割く精度を奪っている**と読める。
   相対出力＋積み上げなら、共有フレームと共有語彙を捨てずに同じ利点を取れる可能性がある。

これが効けば R4 が不要になり、**主表を「デコーダ単体・後段なし」で出せる**。

**R2. codebook の protein/ligand バランスを取る**

§4.1–4.2 の結果を直接叩く手。(a) ligand 原子の損失重み付けは
`source` 列が記述子の中にあるので `_compute_recon_loss` の変更だけで済む。
(b) EMA 側の重み付けは `EMACodebook.forward` が source を持たない flat な
`(B, code_dim)` を受ける設計なので、`weights` 引数を足して cluster_size の積算に
掛ける必要がある。(c) バッチ内の per-source サンプリング比を変える手もあるが、
データ量が動くので (a)(b) を先に試す。

論文としても「joint が負けるのはデータ質量であって共有そのものではない」という
アブレーションになるので、主張が一段強くなる。R1 と同じ run に同居できる。

**R3. VQ をポケット + リガンドの 1 系列にする**

現状の VQ は pocket と ligand を別アイテムとして学習している
（`atom_descriptors.py` の docstring に明記されている）。
つまり「joint」なのは codebook だけで、attention は跨いでいない。
1 系列にすればリガンド原子がポケット原子を見られるようになり、
界面表現が良くなる可能性がある。

**副作用がひとつある。** ポケット文脈に依存するということは、
**同じリガンドでもポケットが違えば別コードになる**ということで、
GEOM のリガンド単独事前学習（空ポケット）との等価性が崩れる。
事前学習 → 複合体 finetune の接続を設計し直す必要があるので、
R1 / R2 とは別腕として扱う。

### 公平性

元の F1–F10 に加えて 3 つ。

- **F11**: CASP16 では `localframe_*` 腕がリガンド指標でも界面指標でも joint を上回っている（§4.4）。
  R4 / R1 適用後に再比較し、joint を主系統にする根拠を表に併記する。
- **F12**: 論文 Table 2 の ProLIT-MLM 行を 90.4 / 76.5 に差し替える（§6.2, W11）。
- **F13**: ポケット緩和を外したので、緩和込みで得られた過去の生成数値
  （Vina Score −5.6 系）は主表から落とす。落とした差分は
  「物理後処理を許した場合の増分」として ablation に置くなら置く。

## 10. 推奨する進め方

力場を成果物から外した以上、幾何の質は R4 と R1 が担うことになる。
両者は狙いが重なるが、コストが一桁違うので順番が決まる。

1. **R4（refiner の再学習）を最初に回す。** §7 のとおり、再学習なしで既に
   oracle の 6 割・ConfSeq と同水準に届いている。VQ を触らないので今すぐ着手でき、
   再構成タスクのゴールがこれ単体で届く可能性がある。
   同時に、外したポケット緩和の役割もここに引き取らせる。
2. **並行して C2（組み立て段）を通す。** 学習不要で、生成側の化学的欠陥
   （断片化・芳香環ゼロ）に直接効く。R4 とは独立なので同時に進められる。
3. **CASP16 データを用意**し、R4 + C2 適用後の再構成表を出す。ここが今の最優先の詰まり。
4. **C4 / C5** で公平性の穴を塞ぎ、100 標的・単一モデルの主系統を確定する。
5. **R1 / R2 / R3 を VQ の腕として並べ、再構成だけで選抜する。**
   再構成指標は VQ 単体で測れるので、下流を回さずに 16h × 各腕で比較できる。
   R1 と R2 は同じ run に同居させ、R3 は事前学習の設計変更を伴うので別腕にする。
6. **勝った 1 本だけ**を再トークン化 → CLM / MLM / ヘッドの鎖に流す。
   3 本とも下流まで流すと数日 × 3 になる（原則 7「賭けの本数を減らす」）。

### やらなくてよいと分かったこと

分析の収穫の半分はこちらだった。以下はいずれも測定で否定された。

- **codebook を大きくする / RVQ で bit を増やす。** §1.1 で量子化は bond 誤差の
  半分しか説明せず、§7 でその残りも後段の学習モデルで消える。
  コード頻度と誤差は無相関（§4.2）なので、利用率を上げる方向も効かない。
  **一番高価な手（トークナイザの作り直し）は正当化されない。**
- **LM を作り直す。** §1.2 で LM は分子の壊れ方に何も足していない。
- **結合知覚のしきい値を調整する。** §5.1 でどの値でも 65% 頭打ち。
- **幾何修復を反復する（グラフを直す目的では）。** §5.2 で 1 回で収束し、
  偽陽性（3 員環）は減らない。ただし**幾何そのものの修復には反復が効く**
  （§7、refiner 1 step → 3 step で全結合通過 0.331 → 0.596）。目的を混同しないこと。

## 付記: R1+R2 を回した結果（2026-08-04）— 効かなかった

§9 の R1（局所幾何の教師）と R2（codebook の protein/ligand バランス）を 1 本の

CASF-2016 と sbdd-bench の標的は学習から除外している（`--exclude-eval-pdbs`）。

held-out（CrossDocked fold0 = test、CASF/sbdd 除外、n=710、平均 20.9 原子）:

| arm | 段 | Kabsch | bond MAE | per-bond | 全結合通過 | 非結合最近接 |
|---|---|---|---|---|---|---|
| **joint (R1+R2)** | 生 | **0.365** | **0.151** | **0.833** | 0.177 | **1.992** |
| joint (v1) | 生 | 0.301 | 0.145 | 0.840 | 0.156 | 2.012 |
| separate | 生 | 0.239 | 0.090 | 0.946 | 0.513 | 2.089 |

**狙った局所幾何は 1 つも改善しなかった。** bond MAE も per-bond 通過も非結合最近接も
わずかに悪化し、Kabsch は 21% 悪化した。学習済み refiner を通した後も逆転しない
（×3 で 0.617 vs v1 の 0.644）。

### 原因 1: `knn_offsets` ヘッドは制約ではなく、ただの補助タスクだった

`coord` ヘッドと `knn_offsets` ヘッドは同じ trunk から出る**独立な出力**である。
つまりモデルは、coord の出力と整合させないまま knn ヘッドだけを満たせる。
実際 `knn_offsets` の損失は 2.856 → 1.010 とよく降りたのに、その情報は座標に
反映されなかった。

**局所幾何を効かせたいなら、デコードされた Cartesian 座標そのものの
ペア距離を罰する必要がある。** §9 R1 で「安い順」の 2 番目に置いた
1-2 / 1-3 距離損失がその形で、1 番目（KNN ヘッド）を選んだのが誤りだった。
安さで選ぶ判断が間違っていた、というのがこの run の主な教訓である。

### 原因 2: clash 項はレバーになっていなかった

損失値が 0.007、重み 5.0 をかけても 0.035 で、`coord` の 0.27 に対して桁が違う。
床を 1.2 → 2.4 Å に上げても勾配としての存在感が無いので、効かないのは当然だった。
床の値ではなく重みの問題である。

### 原因 3: R2 は優遇したモダリティすら改善しなかった

リガンド原子を損失と EMA の両方で 8.3 倍に重み付けしたのに、リガンドの Kabsch は
0.301 → 0.365 と悪化した。優遇した側が悪くなっているので、
「protein に押されている」という §4.2 の診断が正しいとしても、
EMA の重み付けは対処になっていない（codebook を不安定にした可能性がある）。

### 交絡（記録）

対照腕（除外のみ・R1/R2 なし）を回さなかったので、「R1+R2 が効かなかった」のか
「CASF 除外が悪化させた」のかは厳密には分離できていない。除外で減る学習データは
1.69% なので 21% の Kabsch 悪化の原因としては考えにくいが、
**次に VQ を回すときは対照腕を必ず同時に回す。**

### この run で有効だったこと

- CASF/sbdd の除外そのものは正しく機能した（5,216 複合体を保留、train 200,199）
- `--exclude-eval-pdbs` と `prolit.data.holdout` は今後の全 run で使える
- `jobs/submit.py` のスプールパス不具合を発見・修正した（生成スクリプトは
  `$(dirname "$0")/../lib.sh` を読んでいたが、スケジューラはスプールにコピーして
  実行するので解決しない。job 8343676 が 0.02 秒で死んだ）

### 読み方

PB-valid が 0.148 → 0.732 に上がった。落ちていたサブチェックは
`bond_lengths` と `bond_angles` だけだと以前に切り分けてあり、実際に
上がったのもその 2 つ (0.161→0.819, 0.329→0.836) なので、効いた場所と

CASF 除外そのものは幾何にほとんど効いていない (`joint` → `joint_noleak`
で PB-valid +0.020)。除外は正しさのために要るが、数字を作っているのは
局所幾何損失の方である。

### 代償

**この表は幾何しか見ていない。** PoseBusters は与えられた分子の配座を
検査するので、デコードされた元素・電荷・水素数が正しいかは別の話で、
そちらは CrossDocked 上で悪化を確認している (numH の原子単位精度
0.981 → 0.930、その結果 SMILES 完全一致 0.425 → 0.295)。
つまり現状の `joint_bond` は「幾何は勝つが分子が変わる」状態で、
このまま論文の再構成の数字にはできない。

原因は損失の重みが手で置かれていたことにある。`numH` が 0.1、
`bond12` が 5.0 で、両者が同じエンコーダを取り合えば化学側が負ける。
重みを人が決め直すのは同じ問題を先送りするだけなので、決め方そのものを
2 つ用意して回した (job 8369518 / 8369521, node_f×16h, `-p -3`):

- **`scale`**: 各ヘッドを自分自身の移動平均で割る。生の大きさが 4 桁
  違う (coord 0.27 に対し bb_sc 0.0001) ことが手重みの存在理由なので、
  そこを機械的に潰して「相対的な改善速度」で競わせる。
- **`constrained`**: 幾何を目的関数、化学を制約として扱う。
  `min L_geom` s.t. `L_c ≤ target_c`、`target_c` は **`vq_ctrl_p3` が
  実際に到達した各ヘッドの訓練損失**（推測値ではなく実測値）。
  乗数は双対上昇で上げ下げする。

`constrained` の方が目的そのものに近い。欲しいのは「均衡」ではなく
「化学を落とさずに幾何を上げる」という非対称な要求で、均衡ではそれを
書けない。実際 `scale` を短く回すと coord の重みが 0.017 まで下がる。

不確実性重み付け (Kendall et al.) は先に試して発散した
(`exp(-s)L + s/2` の最適点が `exp(-s) = 1/(2L)` なので、損失が 0 に
近づくヘッドの重みが無限大になる。charge が 7.3e6 に達し val/atom_coord
が 1.166 → 1.213 に悪化)。同じ壊れ方を避けるため `constrained` の乗数は
`[0, 1]` に閉じ込めてある。上限 1 は「置き換える手重みがすべて 0.5 以下
だった」ことから来ていて、制約が上限の内側で達成可能だと言える
（対照群がまさにその水準に、より弱い圧力で到達している）。

## 追記 (2026-08-07 夜): 損失の重み付け — 「均衡」は目的ではなかった

### 測ったこと

`joint_bond` は幾何で勝つが化学を落とす（numH の原子単位精度 0.981 → 0.930）。
原因は手で置いた重み（`numH` 0.1 に対し `bond12` 5.0）なので、重みの
**決め方**を 3 通り実際に回して比べた。いずれも `--bond-distance-loss
--clash-floor 2.4 --exclude-eval-pdbs` で、違うのは損失の合成だけ。

| 方式 | 結果 |
|---|---|
| 不確実性重み付け (Kendall et al.) | 発散。`charge` の重み 7.3e6、val/atom_coord 1.166 → 1.213 |
| **スケール均衡 (`scale`)** | **発散。下表** |
| 制約付き (`constrained`) | 実行中 |

### `scale` が壊れた形（job 8369518, 18 epoch 時点）

| 指標 | `vq_scale` | 対照群 `vq_ctrl_p3` |
|---|---|---|
| val/atom_coord | **85.8** | 0.0958 |
| val/atom_element | 4.3e-05 | 0.00099 |
| val/atom_numH | 4.4e-05 | 0.0129 |
| element 精度 | 0.99999 | 0.981 |

実効重み: `aromatic` 7.6e6、`charge` 1.2e6、`element` 4.8e4 に対して
**`coord` 0.012**。化学は完璧に解かれ、幾何は完全に捨てられた。

### なぜそうなるか — 私が config に書いていた説明は間違っていた

`scale` を入れたとき「不確実性重み付けと違って発散しない。比が構成上 1 に
固定されるから」と書いたが、これは誤り。固定されるのは**寄与**であって、
**重み**は `1/損失の移動平均` である。損失が 0 に近づくヘッドの重みは
`exp(-s)` と同じく無限大に伸びる。両者は同じ失敗の別表現でしかなかった。
該当箇所は測定値に置き換えた。

### 分かったこと

**均衡は目的ではない。** 欲しいのは「化学を落とさずに幾何を上げる」という
非対称な要求で、均衡はそれを表現できない。しかも 2 通りの均衡はどちらも、
**簡単な方のタスクに無限の重みを与える**という同じ壊れ方をした。
簡単なタスクほど損失が 0 に近づき、どちらの式でも重みが `1/損失` の形で
効くからである。

`constrained` を残す設計上の理由もここではっきりした。乗数を `[0,1]` に
閉じ込めてあるので、この壊れ方は構成上起こりえない。上限 1 の根拠は
「置き換える手重みがすべて 0.5 以下だった」ことで、対照群がより弱い圧力で
その水準に到達している以上、制約は上限の内側で達成可能である。

`scale` も 100 epoch 完走させた（val/atom_coord 49.3 で終了、codebook 利用率

0.99277 (bond) → 0.99710 で、対照群の 0.99572 より良い。`ring` と `charge`
も同じ。手で置いた重みは、幾何を足したときに化学を守れなかっただけでなく、
**そもそも化学に対して最適でもなかった**ということになる。

**代償は幾何の 11〜15%。** coord 0.1325 → 0.1465、bond12 0.00275 → 0.00321。
CASP16 のエンドツーエンドで、この交換が得か損かが決まる。

**λ が仕組みの説明になっている。** `hybrid` / `ring` / `numH` / `bb_sc` の

`aa` は残基型の予測で、論文の指標には直接効かない。

### 3 方式の総括

均衡を目指した 2 方式（`uncertainty`, `scale`）はどちらも、**簡単な方の
タスクに無限の重みを与えて**壊れた。損失が 0 に近づくヘッドの重みが
`1/損失` の形で発散するからで、これは均衡という目標そのものに内在する。
制約付きは目標が非対称（幾何を上げる / 化学を落とさない）で、乗数に上限が
あるので、この壊れ方が構成上起こらない。

## 追記 (2026-08-08): joint の符号帳は「足りない」のではなく「protein に置かれている」

### なぜ測ったか

`separate` の ligand 化学が joint より良い (0.9804 対 0.9370) 理由として、
2 つの説明があり得た。

1. **符号が足りない** — separate は ligand に専用の 4096 を与えている。
   joint では ligand が取れる符号が少なく、粗く量子化されている。
2. **符号の位置が protein に引っ張られている** — 符号数は足りているが、
   共有符号の重心が 9.3:1 の多数派である protein 原子で決まっている。

打ち手が違う。1 なら EMA の重み（符号の配分）、2 なら損失の重み（encoder が
ligand をどこに写すか）。3 つの checkpoint で ligand / protein 別に
符号の利用を数えた（3 shard × 120 複合体、protein 70,388 原子 / ligand 7,559 原子）。

### 結果

| | ligand が使った異なり符号 | ligand 優勢な符号 | protein 優勢 | ligand の 1 符号あたり原子数 |
|---|---|---|---|---|
| `vq_ctrl_p3` | 4,142 | 396 | 7,637 | 1.8 |
| `vq_bond_p3` | 3,931 | 756 | 7,487 | 1.9 |
| `vq_constrained` | 3,755 | 947 | 7,204 | 2.0 |

### 読み方 — 説明 1 は否定された

**ligand は既に 3,755〜4,142 の異なり符号を使っている。separate が与える
専用帳 4096 とほぼ同数である。** 符号は足りている。1 符号あたり 2.0 原子
なので、粗く量子化されてもいない。

差は**どの符号を使っているか**にある。ligand が触る符号のうち ligand が
多数派なのは 947 個だけで、残りは protein 優勢な符号を間借りしている。
共有符号の重心は 9.3:1 の多数派で決まるので、ligand 原子は
**protein の幾何で位置が決まった符号に量子化されている**。

制約付きでは ligand 優勢な符号が 396 → 947 に増えており、化学の制約を
掛けただけで ligand が符号空間を取り返し始めていることも分かる。
これは方向が正しいことの傍証になる。

### したがって回すべき掃引

`ligand_source_weight` は損失と EMA を同時に動かしていたので、どちらが
効いたのか言えなかった。分離した (`ligand_ema_weight`、既定 None =
損失側に追従、既存の run は挙動不変)。3 点で機構を切り分ける:

| run | 損失重み | EMA 重み | 問い |
|---|---|---|---|
| `vq_lig_loss` | 8.3 | 1.0 | encoder を押せば、重心を動かさずに ligand 専用領域が育つか |
| `vq_lig_ema` | 1.0 | 8.3 | 重心を ligand 側に引けば足りるか |
| `vq_lig_both` | 8.3 | 8.3 | 両方（分離前の設定） |

論文の主張（joint の方が結合界面を捉える）には損失側が望ましい。
EMA を引くと protein の重心が犠牲になるが、損失側は共有空間の中で
2 つのモダリティが**区別できる領域を占める**ように表現を作るからで、
それは「共有語彙が界面を捉える」という主張そのものである。

## 追記 (2026-08-09 深夜): ビットは律速ではない — 残差量子化と codebook 拡大を却下

**汎化である。** 同じ全原子 Kabsch が、分布内 (fold0 test) では 0.283、
CASP16 では 0.638。**2.2 倍の乖離**があり、これが差の主因。

lDDT は局所距離の指標**である。上表のとおり `vq_bond_p3` は量子化を外すと
lDDT が 0.9848 → 0.9938 に上がる = 局所幾何を良くする余地は表現側にまだある。
そこを直接押すのが実行中のイテレーション 1（1-2/1-3 距離をタンパク質原子にも
掛ける）で、この測定はその賭けを支持し、代替案 2 つを消した。

データ多様性の拡張（PDB のポケットを足す）は効くはずだが、コーパス構築が要る。
今回のループの「単純に保つ」方針では採らない。

- lDDT の同等を勝ちに変えるには `dmap` の重みを 1.0 から上げるのが直接的だが、

- 本当の律速（汎化 = CrossDocked の受容体クラスタが ~2,900 しかない）を解くには

## 追記 (2026-08-11): 距離項の 1 本化は失敗 — 局所は長距離に埋もれる

### 何を試したか

損失が複雑すぎる（幾何だけで 5 項、うち 3 つが手重み 5.0/2.0/5.0、しかも
per-source マスク付き）ので、距離の項を 1 本に畳もうとした:

```
L_pair = mean over 全ペア(参照 < 15 Å) of ((d_pred − d_ref) / d_ref)²
```

**相対**誤差にすれば近距離が自動で重くなる、というのが根拠。実際、参照構造で
測ると結合が損失に占める割合は 絶対誤差 0.0085 / 現行の手重み版 0.0371 /
相対誤差 **0.0770** で、手重み 5.0 が買っていた強調を式の形が肩代わりする、
ように見えた。

### 結果 (CASP16 298 複合体)

| arm | bond MAE | angle MAE | PB-valid | TM | lDDT | 勝ち |
|---|---|---|---|---|---|---|
| `joint_dmap`（5 項、局所あり） | **0.075** | **7.51** | **0.685** | 0.852 | 0.953 | 6/8 |
| `joint_simple`（1 項） | 0.233 | 14.39 | 0.084 | 0.794 | 0.897 | 2/8 |
| `joint_simple_clash`（1 項 + clash） | 0.219 | 12.63 | 0.057 | 0.778 | 0.889 | 3/8 |
| `joint_simple_lig`（1 項 + 配位子重み） | 0.150 | 10.06 | 0.258 | 0.806 | 0.909 | 3/8 |

### なぜ外れたか

**15 Å 以内のペアは 1 分子あたり数千あり、結合は数十しかない。** 相対誤差に
しても数の差は覆せず、長距離を合わせる方が総損失を下げやすいので、
結合長・結合角が捨てられる。bond MAE が 3 倍、angle MAE が 2 倍に悪化し、
PB-valid は 0.685 → 0.084 で壊滅した。

根拠にした 0.0770 は**参照構造で測った初期値**であって、学習後の均衡を
予測するものではなかった。ここが読み違いである。

3 本が同じ方向を指しているのが強い:

- `clash` を戻しても直らない (0.084 → 0.057)。clash は接触を防ぐ項であって
  結合長を直す項ではないので、筋は通っている。
- 配位子重み 8.3 は bond MAE を 0.233 → 0.150 まで**部分的に**戻すが、
  0.075 には届かない。原子全体の重みを上げても、ペア数の優位は覆せない。

### 論文にとっての意味

「なぜ距離のスケールごとに項を分けるのか」に測定で答えられるようになった。
これまで「エイヤで 5 項」だったものが「1 項では足りないと測った」に変わる。
査読で必ず突かれる箇所が、そのまま ablation の 1 行になる。

### 次に試していること (job 8389449 / 8389450)

局所と長距離の**分離は残したまま**、手重みと per-source マスクだけを消す:

- `local` = 1-2 と 1-3 の**和集合**を相対誤差で。5.0 と 2.0 の比が消える。
  結合検出は既存の共有結合半径のままなので、新しい定数は増えない。
- `dmap` = 15 Å 以内。local が全原子になったので dmap も全原子に。
  **項は距離で分かれるのであって source では分かれない**、という形に統一。
- 重みは coord / local / dmap すべて 1.0。

`vq_local_noclash` (clash も落とす) が通れば、幾何の目的関数は
**重み 1.0 の 3 項、per-source マスクなし、手決めの定数は 15 Å だけ**になる。

## 追記 (2026-08-12): 学習は node_f ではなく gpu_1 で回す

### きっかけ

「node_f の 4 GPU をちゃんと使えているのか」という問いから確認したところ、
`--devices 1` を明示しているため **1 枚しか使っていなかった**。node_f を
1.0 pt/node-hour で借りて GPU の 25% しか動かしていない状態だった。

### ベンチマーク (4 epoch、同一設定・同一 seed、-p -3 で並行)

| run | 資源 | 設定 | 実時間 | pt/h | 実費 |
|---|---|---|---|---|---|
| `b_gpu1` | node_f | 1 GPU / batch 256 | 23.1 分 | 1.0 | 0.385 pt |
| **`b_slice`** | **gpu_1** | 1 GPU / batch 256 | **23.5 分** | **0.25** | **0.098 pt** |
| `b_ddp2` | node_f | 2 GPU / batch 128 | 28.7 分 | 1.0 | 0.478 pt |
| `b_ddp4b` | node_f | 4 GPU / batch 256 | 24.9 分 | 1.0 | 0.415 pt |
| `b_ddp4` | node_f | 4 GPU / batch 64 | 39.7 分 | 1.0 | 0.662 pt |

### 結論 1 — gpu_1 は node_f と同速で 1/4 の価格

差は 1.7%。`pipelines/train/vqvae.py` の `--devices` ヘルプにある
「one full node_f H100 is faster than ... a gpu_1 slice」は測定と合わない。
**これまでの全学習が 4 倍の値段で回っていた。**

### 結論 2 — DDP は追わない

GPU を増やすほど遅くなる (23.1 → 28.7 → 39.7 分)。原因は通信ではなく、
**データが分割されていない**こと: `AtomShardedDataset` は `IterableDataset`
なので Lightning が `DistributedSampler` を注入できず、全 rank が全シャードを
読む。そこへ勾配同期のコストだけが乗る。

rank 分割を入れると**デッドロックする**。シャードは 2,838〜15,365 件と
ばらついており、`i % world` で配ると 4 rank の担当が
77,059 / 87,304 / 90,364 / 96,279 件（25% の開き）になる。先に尽きた rank が
epoch 終端の all-reduce で待ち続ける。揃えるには最短の rank に切り詰める、
つまり毎 epoch データの 1/5 を捨てることになる。

**そこまでして得られるのは node_f 上での 4 倍速だが、gpu_1 に移すだけで
同じ 4 倍の節約が実装リスクゼロで手に入る。** 差し戻し、理由を
`atom_descriptors.py` の `__iter__` に測定値つきで残した。

### 反省

3 回続けて外した。(1) rank 分割の欠落を「通信律速」と誤解、
(2) `__iter__`（fork された worker）で `is_initialized()` が使えると誤解、
(3) 不揃いなシャード分割がデッドロックを招くことを見落とし。
プログレスバーの分母 6257 は `__len__`（分割前の全長）由来で、
**実際の step 数ではない**。判定に使ってはいけない。

### 続き — DDP は直った (2026-08-12 深夜)

「gpu_1 に移せば同じ 4 倍の節約が手に入る」と書いて DDP を諦めたのは早計だった。
**コストの話だけで、実時間の話を落としていた。**

シャード「内」でエントリを分ければ rank 間が揃う:

| 分け方 | 4 rank の担当 | 最大差 |
|---|---|---|
| シャード単位（最初に試した） | 77,059〜96,279 | 19,220 件 → デッドロック |
| **シャード内でエントリを分割** | 175,474〜175,524 | **50 件**、`drop_last` が吸収 |

投入前にローカルで検証した（`_dist_rank_world` を差し替えて world=1/2/4 を模擬）。
バッチ数は 4 rank とも完全に一致。

| 設定 | step/epoch | 4 epoch | 速度比 | pt/h | 実費 |
|---|---|---|---|---|---|
| 1 GPU node_f | 1565 | 23.1 分 | 1.00x | 1.0 | 0.385 pt |
| 2 GPU node_f | 782 | 13.8 分 | 1.67x | 1.0 | 0.230 pt |
| **4 GPU node_f** | **391** | **9.1 分** | **2.54x** | 1.0 | 0.152 pt |
| 1 GPU gpu_1 | 1565 | 23.5 分 | 0.98x | 0.25 | **0.098 pt** |

step は正確に 1/N。速度比が劣線形 (2 GPU で理論値の 84%、4 GPU で 64%) なのは
**各 rank が全シャードファイルを開く I/O が固定費として残る**ため。計算だけが
1/N になるので、GPU を増やすほど固定費の比重が上がる。

**選択は目的次第**: 最安は gpu_1 (0.098 pt)、最速は node_f 4 GPU (9.1 分)。
実費の差は 1.5 倍、実時間の差は 2.5 倍。ループを速く回したいときは後者。

`__len__` が分割前の全長を返していた点も直した。プログレスバーの分母がここから
来ており、「分割が効いていない」という 2 回の誤読の原因だった。

## タンパク質には局所項が一度も掛かっていなかった

dump から実測 (n=80):

| arm | protein 1-2 MAE | ligand 1-2 MAE |
|---|---|---|
| `joint_dmap` | 0.228 | 0.072 |
| `joint_e250_lig` | 0.198 | 0.078 |
| `joint_local` (全原子に相対誤差の局所項) | 0.225 | 0.188 |
| `joint_pbond_lig` (bond12/13 を全原子に、dmap なし) | **0.160** | — |

`bond_distance_all_sources` を付けない限り 1-2/1-3 はリガンド行だけで、
タンパク質は dmap (15 Å 内の全ペア) しか持たない。これは**リガンドから局所項を
外した時に bond MAE が 0.233 に劣化した状態そのもの**。lDDT は局所距離の指標
なので、ここが効いている可能性が高い。

重要なのは形式の違い: `joint_local` の相対誤差 1 項 (weight 1.0) を全原子に
掛けても protein は 0.225 で動かない。効いたのは `bond12`=5.0 / `bond13`=2.0 の
絶対二乗の方 (0.160)。ただしそちらは dmap を持たないので長距離を失う
(lDDT 0.936)。

→ **protein bonds x dmap の 2x2 で 1 マス空いている**。job 8402932/8402933 で
`joint_e250_lig3` + `--bond-distance-all-sources` を seed 7/8 の 2 本。
seed 2 本にしたのは上の非単調性にノイズ幅が無いため。

## 4 GPU DDP では validation が一度も走っていなかった (2026-08-13)

`--devices 4` の run は**エラーを出さずに best checkpoint を 0 本しか作らない**。
`val/atom_coord` が一度も log されないので `ModelCheckpoint(monitor=...)` が発火せず、
`last.ckpt` だけが残る。

| run | rank 分割 | Validation バー |
|---|---|---|
| `b_ddp2` / `b_ddp4` / `b_ddp4b` | なし | 1396 / 2788 / 700 回 |
| `b_ddp4fix` / `b_shard2` / `b_shard4` / `b_range4` | あり | **0 回** |

### 真因は `__len__` と実 yield のずれ

Lightning は training epoch の末尾を `batch_idx + 1 == num_training_batches` で
判定し、そこで validation を起動する。`num_training_batches` は
`len(dataloader)` = `AtomShardedDataset.__len__` 由来。ところが `drop_last` は
**worker ごと**に効くので実際の batch 数は `Σ_w floor(items_w / B)` で、
`__len__` が返していた `floor(Σ_w items_w / B)` より小さい。

- 1 GPU: 申告 1565 / 実際 1565 → 一致するので validation が走る
- 4 GPU: 申告 **391** / 実際 **382** → 条件が永遠に成立せず、epoch は
  StopIteration で終わり **validation が起動しない**

1 GPU でたまたま一致していたことが、この不具合を隠していた。

### 直したもの

1. `__len__` を `Σ_w floor(items_w / B) × B` に変更（`batch_size` と
   `num_workers` を dataset に渡す。真の値が両方に依存する以上、片方でも
   欠けたら正しく出せない）。world=4 で 382 と一致することを確認。
2. val/test は rank 分割しない (`shard_by_rank=False`)。全 rank が同じ val を
   見るので batch 数が構造的に揃う。val はデータの 1 割なので 4 倍冗長でも安い。

job 8403157 で確認: exit 0、Validation バー 332 行、
`atomvqvae-epoch=00-val` / `=01-val` の best checkpoint が生成された。

### 走行中の 2 本 (8402932/8402933) は止めない

修正前に投入したので best checkpoint は出ないが、`last.ckpt` との差は小さい。
250 epoch の 3 本で実測した last と best の `val/atom_coord`:

## 単一 modality x DDP は未使用パラメータで落ちる (2026-08-13)

`--modality ligand --devices 4` は 4 分で exit 1:

```
RuntimeError: It looks like your LightningModule has parameters that were not
used in producing the loss returned by training_step.
```

`aa` / `bb_sc` は protein 行だけで採点される (`ATOM_PROTEIN_ONLY_HEADS`) ので、

protein のみの run (`vq_sep_prot`) は落ちない。そちらが切るのは 1-2/1-3 と

`strategy="ddp_find_unused_parameters_true"` にした。joint は既定の速い経路のまま。
`--devices` 未指定は node_f では 4 に解決されるので、単一 GPU 扱いにしない。

## refiner を CASP16 に当ててはいけない (2026-08-14)

## 幾何の重みを Optuna で探索した (2026-08-15)

trial 間の比較に使えない。スカラー化せず 2 目的の Pareto 前線を出した。

|---|---|---|---|---|---|---|

| #12 | 0.4042 | 0.0817 | 28.24 | 5.97 | 1.81 | 1.03 |

**手設定 (bond12 5.0 / bond13 2.0 / clash 5.0 / dmap 1.0) は既に前線の上にある。**

論文の主張が界面とタンパク質側の頑健性である以上、リガンド寄りの点に動かす
動機は薄い。動かすなら #5 (bond12 20.63、ligand -16% / protein +0.049) が
最も割が良いが、**15 epoch の代理指標**なので 250 epoch で順位が保たれる保証は
ない (100 epoch ですら逆転した実績あり)。採用前に本番長での確認が要る。

### 分散正規化との突き合わせ

素朴な分散正規化が含意した bond12:dmap = 1200:1 は、前線の最もリガンド寄りの
端 (#7 の 44:0.08 = 553:1) すら超えている。**あの正規化は前線の外側を指していた**
ことが探索で裏付けられた。許容幅ベース (bond12 6.25 / dmap 4) は #4 と #5 の
間あたりで、前線上の妥当な領域を指していた。

## refiner の再学習は失敗した (2026-08-16)

現行トークナイザ (`vq_e250_lig3`) の誤差分布で refiner を作り直したが、
**旧 refiner より悪い**。

| | コーパス | 到達 r | epoch |
|---|---|---|---|
| `refine_geo_v2` (旧) | `pose_refine_atom_noleak`、6,559 複合体 | **0.577** | 11 (8 h で walltime) |
| `refit_e250lig3` (新) | `pose_refine_e250lig3`、6,534 複合体 | **0.850** | 17 (12 h で walltime) |

目標は現行リガンドの Kabsch **0.329** を下回ること。届いていない。

**打ち切りではなく平坦化**: e15 0.8529 → e16 0.8499 → e17 0.8524 と反転している
ので、walltime を伸ばしても届かない。学習率・モデル容量・`sigma_max` のいずれかが

規模はほぼ同じ (train records 25,352 vs 25,396) なので、違いは

`sigma_max=0.7` のノイズが支配的なはずなので、それだけでは 0.577 → 0.850 の差を

## Optuna 前線 #5 を 250 epoch で確認 → 8 指標すべて悪化 (2026-08-16)

`vq_opt5` = `joint_e250_lig3` の幾何重みを前線の中間点に移したもの
(bond12 20.63 / bond13 6.94 / clash 3.56 / dmap 2.38、coord 1.0 固定)。
250 epoch、node_f 4 GPU、5.63 h。

| 指標 | `joint_e250_lig3` | `joint_opt5` | 差 |
|---|---|---|---|
| TM | **0.881** | 0.839 | -0.042 |
| lDDT | **0.964** | 0.949 | -0.015 |
| P-Kabsch | **0.417** | 0.508 | +0.091 |
| lDDT-PLI | **0.945** | 0.925 | -0.020 |
| Contact-F1 | **0.688** | 0.643 | -0.045 |
| PB-valid | **0.668** | 0.648 | -0.020 |
| L-Kabsch | **0.329** | 0.402 | +0.074 |
| SMILES | **0.416** | 0.315 | -0.101 |

seed ノイズ幅 (TM 0.025 / lDDT 0.016 / SMILES 0.047 / L-Kabsch 0.005) と比べて
TM・SMILES・L-Kabsch の劣化は明確にノイズを超える。

**代理指標が順位でなく符号を外した。** 15 epoch では #5 がリガンドの
bond12_mae を 0.105 -> 0.088 に改善すると出ていたのに、250 epoch のベンチでは
リガンド指標が軒並み悪化した。最適化していた当の軸で逆を向いている。

### 短い学習が順位を誤らせた事例はこれで 3 件

1. joint vs separate: 100 epoch では separate がリガンド指標で勝ち、250 で逆転
2. リガンド重み: 100 epoch では「幾何を犠牲にする」に見え、250 で消滅
3. 幾何の重み: 15 epoch の Pareto 前線が 250 epoch で符号ごと崩れた

**この問題設定では短い代理での最適化は機能しない。** epoch を増やせば trial が
減り、減らせば符号が信用できない。Optuna を使うなら trial あたり 250 epoch
(4.9 pt) が要り、20 trial で 98 pt になる。割に合わない。

### 結論

手設定 (bond12 5.0 / bond13 2.0 / clash 5.0 / dmap 1.0) を据え置く。Optuna の
価値は改善を見つけたことではなく、**手設定が前線の妥当な位置にあると確認し、
かつ短い代理が使えないと示したこと**。

## CLM / MLM の学習データレシピ（`jobs/archive/` から復元、2026-08-16）

コーパス構築には `run.json` が無く、`jobs/archive/` のスクリプトだけが出所。
再トークン化のたびに失われかねないので、ここに写す。

### CLM は 2 段

**段 1 — 事前学習** (`job_build_pretrain_mixed_joint.sh`):

```
mix.py --inputs data/lm_tokens_geom_allatom \
                data/lm_tokens_protein_plinder_nocasf \
       --out-dir data/lm_tokens_pretrain_mixed_joint
```

GEOM の**リガンド単体**（空ポケット形式）と Plinder の**タンパク質単体**の混合。

**段 2 — 複合体 finetune** (`job_lm_fullft_joint.sh`):

```
clm.py --token-dir data/lm_tokens_allatom_full_joint \
       --atom-codebook-size 8192 --mask-prompt \
       --init-from pocket-ligand-lm/lm_pretrain_joint2/checkpoints/last.ckpt \
       --micro-batch-size 64 --lr 3e-4 --max-epochs 3 --early-stop-patience 2
```

### MLM は 4 コーパス混合の 1 段 (`job_build_train_mlm_nocasf.sh`)

```
mix.py --inputs data/lm_tokens_protein_plinder_nocasf \
                data/lm_tokens_complex_plinder_nocasf \
                data/lm_tokens_allatom_nocasf \
                data/lm_tokens_complex_biolip \
       --out-dir data/lm_tokens_pretrain_nocasf
mlm.py --token-dir data/lm_tokens_pretrain_nocasf --atom-codebook-size 8192 \
       --micro-batch-size 256 --num-workers 7 --max-epochs 3 --early-stop-patience 2
```

その後 pose ヘッド群 (`scoring_head.py`) を学習してアンサンブル。

### 再トークン化に必要なもの

| # | コーパス | 用途 | 生成元 |
|---|---|---|---|
| 1 | `geom_allatom` | CLM 事前学習 | `tokenize_geom.py` |
| 2 | `protein_plinder_nocasf` | CLM 事前学習 + MLM | `tokenize_plinder.py` |
| 3 | `allatom_full_joint` x10 | CLM 本学習 | `tokenize_crossdocked.py` |
| 4 | `complex_plinder_nocasf` | MLM | `tokenize_plinder.py` |
| 5 | `allatom_nocasf` | MLM | `tokenize_crossdocked.py` |

80 分の 1 の規模で学習してしまう。正規化統計は両キャッシュで完全一致するので、
そちらの取り違えは起きない。

**GEOM 事前学習は 2026-06 時点では効果なしと測定されている**
(finetune が scratch より僅かに悪い)。それでも段 1 を維持するのは、
過去の数値と条件を揃えるため。効果の再評価は別途。
