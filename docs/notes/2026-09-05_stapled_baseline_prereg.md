# 事前登録: 既存トークナイザを貼り合わせた baseline (ESM3 × ConfSeq)

2026-09-05。判定規則を測定前に固定する。結果を見てから比較対象・指標・
検定を選ばない (`docs/notes` の過去 5 件で踏んだ罠)。

## 問い

論文の主張は「protein と ligand を**一つの共有語彙・共有フレーム**で離散化する
ことに意味がある」である。これに対する最も自然な反論は

> 既存のタンパク質専用トークナイザ (ESM3, FoldToken) と
> リガンド専用トークナイザ (ConfSeq, Token-Mol) を**貼り合わせれば済む**のでは

であり、現在の論文にはこれに答える行が無い。既にある `separate` アブレーションは
**自前の VQ を 2 本に割った**ものなので、この反論には答えていない。

## baseline の構成

**ESM3 structure tokenizer × ConfSeq**。各モダリティで再構成が最良の既存手法を
選ぶ (`docs/results/2026-09-05_posebusters.md`, n=428):

| | 指標 | ProLIT | 選んだ既存手法 |
|---|---|---|---|
| protein | pocket Kabsch / lDDT | 0.314 / 0.990 (all-atom) | ESM3 1.202 / 0.907 (backbone) |
| ligand | PB-valid | 0.491 | **ConfSeq 0.699** |
| ligand | bond MAE | 0.122 | **ConfSeq 0.040** |

ConfSeq はリガンド化学で ProLIT に**勝っている**。弱い相手を選んだのではない。

トークン列:

```
<bos><p> ESM3 structure tokens (pocket 残基ごとに 1 個) </p>
      <l> [pose tokens] ConfSeq tokens </l><eos>
```

### ポーズチャネル (これが無いと baseline は原理的に成立しない)

ESM3 構造トークンは残基ローカル幾何、ConfSeq は SMILES + 離散化した二面角・
結合角で、**どちらもリガンドの受容体内での配置を持たない**。連結しても剛体変換
6 自由度が欠落する。したがって baseline には明示的なポーズトークンを与える:

- 並進: ポケット bounding box を一辺 `2**(bits/3)` 分割した立方格子
- 回転: 決定的に生成した `2**bits` 個の単位四元数から最近傍 (q と −q は同一視)

量子化器は `own_allatom_reconstruct_cli.quantize_pose` (localframe アームで
既に使っているもの) と**同一の実装**を使う。アームごとに別の量子化器を使うと
比較にならないので、`prolit` に移して 1 箇所にする。

ProLIT 側のポーズ予算は **0 ビット** (共有フレームで原子ごとに暗黙符号化)。
主張は差分で書く: 「ProLIT は追加 0 ビットでこの界面品質を出す。貼り合わせ構成
が並ぶには N ビット要る」。

## 測る 2 つのこと

### A. 再構成 (Table 1) — ポーズ予算スイープ

- 評価集合: **PoseBusters Benchmark 428 複合体**
  (`benchmarks/recon-bench`, 既存の n=428 対応あり検定がそのまま効く)
- アーム: `stapled_pose{0,13,26,39}` + `stapled_oracle`
- ProLIT 側は既存の `joint_e250_lig3` complex 行

**スコープの制約を先に書いておく**: ESM3 は backbone (N/CA/C) しか復元しない。
したがって界面指標 (lDDT-PLI, Contact-F1) は**両アームとも backbone 限定**で
計算する。ProLIT の all-atom 値と直接並べない。並べたら反則。

**主要な読み**: lDDT-PLI (backbone scope) が ProLIT の値に並ぶのに必要な
pose bits。これが break-even 点。

### B. ポーズ・リスコアリング (Table 2) — MLM 比較

**追加 (2026-09-05, ユーザ指示)**。生成だけでなくリスコアリングでも測る。
こちらのほうが構造的な主張が鋭い。

同じ複合体の複数ポーズを見分けるとき、貼り合わせ列で**ポーズ間に変わるのは**

- ポーズトークン 3 個 (39 bit)
- ConfSeq の二面角・結合角トークン (リガンドの内部配座)

の 2 つだけである。**ESM3 のポケットトークンは全ポーズで完全に同一**
(受容体は動かない)。つまり貼り合わせリスコアラは、剛体配置の情報を
**3 トークンからしか読めない**。ProLIT はリガンド原子トークン ~25 個の
すべてが共有フレームの座標なので、配置がトークン列全体に分布している。

- 学習: `pipelines/train/mlm.py` を貼り合わせコーパスで。層数・hidden・
  マスク率・ステップ数は `mlm_e250lig3` と同一
- ヘッド: `pipelines/train/scoring_head.py`。デコイコーパスは
  `tokenize_decoys.py` を貼り合わせモードで再生成 (同じ複合体・同じ decoy 生成規則)
- 評価: `pose_rescoring_bench`、CASF-2016 284 標的、decoys-only、
  **既存の `joint_nocasf` / `separate` 行と同じプロトコル**
- 主要指標: top1 <2 A、副次に top1 <1 A と Spearman rho

**予測 (測る前に書く)**: 貼り合わせ側は 39 bit の量子化ポーズしか持たないので、
CASF の近傍デコイ (0-1 A 帯、ここで docking power が決まる) を**原理的に
分離できない**。39 bit の並進セルは箱 25 A / 80 分割 = 0.31 A、回転は
2^20 方位。0-1 A 帯のデコイはこの分解能では区別できるが、
**ConfSeq が内部配座しか持たないため、剛体だけずれたデコイは
ポーズトークン以外まったく同じ列になる**。top1 <1 A で大きく落ちると予測する。
落ちなければ予測が外れたと書く。

- 評価: sbdd-bench 100 ポケット × 100 分子、**ML のみ** (数値最適化なし)、

**トークン数は揃わない** (ProLIT 1 tok/原子, ConfSeq 3.66 tok/重原子 +

## 判定規則 (測定前に固定)

- 対応のある検定。標的/複合体でペアを取り、`prolit_bench.stats` の
  Wilcoxon + bootstrap CI + Holm 補正。閾値 p < 0.05
- 生成の主要指標は **Vina Score**、副次に PB-valid と clash-free。
  「score だけ良くて PB が落ちる」腕は採用しない (反復デコードで踏んだ罠)
- 再構成の主要指標は **lDDT-PLI (backbone scope)**、副次に Contact-F1

## ProLIT が負ける条件 (先に書く)

以下が起きたら論文の主張はそのままでは書けない。書き換える。

1. pose 39 bit の baseline が **lDDT-PLI で ProLIT に並ぶか上回る**
   → 「共有フレームでなければ界面は表現できない」は言えない。
   言えるのは「同じ品質をより少ないビットで出せる」というレートの話だけになる
2. baseline LM の **Vina Score が ProLIT-CLM 以上**
   → 生成タスクで貼り合わせ構成に負けている。Table 3 の主張を撤回する
3. pose 0 bit でも baseline の Contact-F1 が非自明に高い
   → 量子化器かフレームの実装バグ。結論ではなく実装を疑う

## 実施順 (安い順・各段が独立に意味を持つ)

1. ✅ `prolit` に pose 量子化器を降ろす (recon と corpus builder の両方が要る)
2. ✅ recon-bench に `stapled` アダプタ → A のスイープ (node_q)
3. ESM3 pocket トークンのキャッシュ (GPU)
4. `tokenize_stapled.py` でコーパス。**B と C で同じコーパスを使う**
5. MLM 学習 (node_f) → pose head → CASF 評価  ← B
6. CLM 学習 (node_f) → 生成 → 100 ポケット評価  ← C

B を先に回す。パイプラインが既存で、CASF の対応あり検定が 284 標的で効き、
上の予測が当たるか外れるかが一番はっきり出るため。

## 実装メモ (実行中に確定した事実)

### ConfSeq の被覆率は実質 100%。ただし CASF は mol2 から読むこと

| 集合 | 読み方 | n | encode | 完全ラウンドトリップ |
|---|---|---:|---:|---:|
| PoseBusters Benchmark | sdf | 428 | 428 | **428** |
| CASF-2016 coreset | **sdf** | 285 | 190 | **0** |
| CASF-2016 coreset | **mol2** | 285 | 285 | **285** |

詳細は `2026-09-05_confseq_coverage_was_the_sdf.md`。リスコアリングの評価経路は
デコイを `decoys_docking/*_decoys.mol2` から `parse_mol2_multi` で読んでおり
(native は decoys-only プロトコルで採点されない) 、**ConfSeq に不利な SDF 経路を
通らない**ので問題ない。

### BioLiP のデコイポーズでは 24% が ConfSeq で表現できない

`--build-stapled-vocab` パスで実測 (n=8,721 ポーズ / 4,000 複合体サンプル):
**2,112 件 (24.2%) が encode 失敗**。結晶リガンドが 100% 通るのと対照的。
これが分子単位か配座単位かで意味が変わる (分子単位なら学習集合が
ConfSeq 向きの分子に偏る、配座単位なら**歪んだポーズが系統的に落ちる**——
リスコアラにとって後者のほうが悪い)。native のみの失敗率を測定中。

**どちらであれ両アームで同じ複合体集合を使えなくなる**ので、
ProLIT 側も同じ「ConfSeq が通ったポーズ」に制限して比較するか、
落ちた分を明示して報告するかを、数字を見てから決める。ここは事前登録では
決められないので、**決め方だけ先に固定する**: ProLIT 側を制限した数字を主報告
とし、非制限の数字を併記する (baseline に有利な側を主にする)。

### ConfSeq の語彙は幾何側を列挙して固定する

ConfSeq は二面角・結合角を `<整数度>` で書くので、幾何側のアルファベットは
閉じた集合である。`build_vocab` は `<-180>`..`<180>` を**列挙**して union し、
化学記号だけをデータから観測する。こうしないと「native が取らなかった角度を
デコイが取る」だけで語彙外になり、**リスコアラが最も必要とする歪んだポーズが
コーパスから消える**。実測語彙 398 (観測 396)。

### 依存関係

ConfSeq は Indigo / SmilesPE / timeout-decorator を要求する。`pyproject.toml` に
`[dependency-groups] stapled` を足した (`uv sync --group stapled`)。SmilesPE は
gensim を宣言していて、uv が workspace 全体を 1 環境で解決する都合上
共有 pin を動かす (starlette 1.0.0 -> 1.6.0) ため**宣言から外し**、
`uv pip install --no-deps smilespe==0.0.3` を README に書く。
lock には idna 3.11 -> 3.19 と starlette 1.0.0 -> 1.6.0 が入った (marimo 系)。

### TSUBAME: node_q は MIG スライスを渡してくる

最初の投入 (job 8572718, node_q) は `gn_mig=2` を割り当てられ、torch から GPU が

`run_reconstruction.py --require-cuda` を足して、GPU が無ければ即座に落ちるように

## 実装メモ

- pose 量子化器は `prolit.tokenizers.pose_budget`。移す際に**予算超過のバグ**を
  発見・修正した (39 bit で 1 軸 81 分割 = 531,441 セルを 524,288 セル分の
  値段で使っていた)。13 / 26 bit は不変なので既存の localframe 行に影響なし
- ESM3 は**全鎖を符号化してポケット残基を読み出す** (`protein_scope="full"`)。
  ポケットだけ符号化すると 1..L に振り直すせいで数 A 離れた残基が鎖の隣に
  なり、backbone Kabsch が 0.30 -> 8.48 A に崩れる。これは我々が課した
  ハンデであって ESM3 の性質ではない
- ConfSeq は PoseBusters 428 リガンド**全件**を符号化できる。語彙 391
  (8.61 bit/token)、2.88 token/重原子 = **24.8 bit/重原子**。
  ProLIT は 13.0 bit/重原子でポーズ込み

# 追記 (2026-09-05 夕): 再構成の結果を受けた LM 側の事前登録

再構成の結果は `docs/results/2026-09-05_stapled_baseline_reconstruction.md`。
**予想が外れた**: break-even は存在しない。oracle 配置 (真の剛体変換を無償)
でも貼り合わせ構成は lDDT-PLI で 0.107、Contact-F1 で 0.131 負ける。
配置ビットは 3 トークンで飽和し、残る差は**2 つのデコーダの誤差が独立である
こと**から来る。

## LM 側のポーズトークンの割り付けを変える (実行前に宣言)

再構成では 39 ビットを 1 つの整数として使い、base-8192 の 3 桁に分けていた。
**LM ではこの分け方は不当に不利**である: 桁の境界が並進ラスタと回転インデックス
を跨ぐので、0.3 A しか違わないポーズが全く無関係なトークン id になる。
ポーズ符号が距離を保存しない = ハッシュであり、モデルは 39 ビットの
ルックアップを暗記するしかない。

そこで LM 用は**意味のある階層トークン**に割り付け直す。

**当初は 3 トークン (39 ビット) のつもりだったが、実測して 4 トークンに変えた。**
30 A の箱で 400 個の無作為配置を量子化して測った結果:

| 割り付け | 並進誤差 (中央/最大) | 回転誤差 (中央/最大) |
|---|---|---|
| 39 bit を 1 整数に詰める (再構成側) | 0.189 / 0.283 A | 1.35 / 2.81 度 |
| 3 トークン (並進 1 + 回転 2) | **0.751 / 1.181 A** | 0.81 / 1.64 度 |
| 3 トークン (並進 2 + 回転 1) | 0.037 A | **最大 16 度 = 縁で 0.8 A** |
| **4 トークン (並進 2 + 回転 2)** | **0.037 / 0.059 A** | **0.81 / 1.64 度 (= 0.042 A)** |

3 トークンではどう割っても**量子化器自身の誤差が 0-1 A 帯に入る**。
docking power はその帯で決まるので、それでは実験が測るのは表現ではなく
**私の量子化器**になる。4 トークン (51.93 ビット) なら配置誤差は約 0.06 A で、
下流のどの指標よりも 1 桁小さい。

再構成側の量子化器は変えない (公表済みの localframe 行と同じ曲線に乗せるため)。
**LM アームだけ 13 ビット多く使う**ことになるが、これは baseline に有利な変更で
あり、再構成表は oracle 配置ですら ProLIT が勝つことを既に示している。
レート列に明記し、脚注で割り付けの違いを述べる。

## 予測 (測る前に書く)

### リスコアリング (Table 2)

同じ複合体の複数ポーズで変わるのは 3 ポーズトークンと ConfSeq の角度トークン
だけ。ESM3 のポケット接頭辞は全ポーズで同一。したがって:

- **DP@2A**: 貼り合わせ側は 60-80% と予測 (ProLIT の 96.1% に対し大きく劣る)。
  遠いデコイを弾くのは並進セルだけで足りるので、全滅はしない
- **DP@1A**: **40% 以下**と予測 (ProLIT 82.7%)。0-1 A 帯の判別は回転細トークン
  1 個に集約されており、しかも隣接ポーズが隣接 id にならない
- **Spearman rho**: 0.6-0.75 と予測 (ProLIT 0.895)

**外れたら外れたと書く。** 特に DP@1A が 60% を超えたら、
「配置がトークン列全体に分布していること」の価値は過大評価だったことになる。

### 生成 (Table 3)

CLM は 3 トークンで配置を当てなければならない。並進セル 1.5 A 刻みを当てるのは
ポケット条件付きなら学習可能だが、回転 2 トークンは事実上の暗記になる。

- **Vina Score**: ProLIT より 2 kcal/mol 以上悪いと予測
- **PB-valid**: ConfSeq の内部幾何が良いので **ProLIT を上回る**と予測
  (再構成で結合長 MAE 0.040 vs 0.122、結合角 2.27 vs 10.08 度)。
  ここは貼り合わせ側が勝つと予測しており、そう書く

### 共通

ConfSeq が encode できない複合体が BioLiP の 24.2% ある (分子単位、
native も decoy も同じ率なので配座依存ではない)。
**主報告は ProLIT 側も同じ 75.8% の複合体に制限した数字**とし、
制限なしを併記する (事前登録どおり、baseline に有利な側を主にする)。

`merge_vocabs` はソース順に依存しない (頻度でなく名前順)。

**語彙が小さいと失われるものが大きい**: 40 バケット分の語彙 (385 トークン) で
デコイの失敗率は 33%、3 バケット分 (376) では 59% だった。差は OOV である。
純粋な ConfSeq encode 失敗率は別に測って **24.2%** (分子単位、native も decoy も
同率)。最終語彙では OOV はほぼ消えるはずで、残る 24% が本当の被覆率の上限。

### 回転 augmentation の非対称性 (報告する)

ProLIT の GEOM コーパスは 1 コンフォマーを 8 回転して 11.6M docs / 361M tokens に
している。**貼り合わせ側にこの augmentation は存在しない** (ESM3 も ConfSeq も
不変なので 8 個の同一文書になる)。したがって GEOM は 1.47M docs / 約 107M tokens。
これは表現の性質であって手心ではないので、**水増しせずに報告し**、
学習ステップ数を揃えてトークン数はレート列に併記する。


## ConfSeq 語彙は定数にした (2026-09-06)

当初は「幾何側 (角度) は列挙、化学記号はデータから観測」という設計だった。
これは**危険**だった。観測が足りないと OOV になり、OOV は例外ではなく
**その分子を黙って捨てる**。396 コンフォマーから集めた語彙は `#` `o` `s` `r`
を欠いていて、それだけで GEOM サンプルの 63% が消えていた。

実測すると **ConfSeq のトークンは全部 1 文字だった**: `Cl` -> `C` + `l`、
`[nH]` -> `[` + `n` + `H` + `]`、`%10` -> `%` + `1` + `0`。角度以外に
複数文字のトークンは存在しない。つまり**アルファベットは完全に閉じている**。

そこで A-Z / a-z / 0-9 / 記号 21 種 + 角度 361 種 = **445 トークンを列挙**して
語彙を定数にした (`data/stapled/confseq_vocab.json`, LM 語彙 12,740)。
GEOM 3 万分子と BioLiP の観測が 1 つも列挙から外れないことを確認済み。
データパスに依存しないので再現可能で、サンプルサイズを間違えようがない。

`build_vocab(counts)` は `counts` を残してある。列挙に無いトークンが来たら
**それは仮定が壊れた合図**なので、黙って吸収せず語彙サイズが変わるようにした
(`tests/test_stapled_vocab.py` が固定)。

## 被覆率の内訳を分けたら 24% は 15% だった

失敗を理由別に数えたら、当初「ConfSeq が 24% 表現できない」と書いていた数字の
内訳が違った (デコイ 221 ポーズ, BioLiP):

| 理由 | 当初 | 修正後 |
|---|---|---|
| `failed_oov` (語彙不足 = **ビルド誤り**) | 15% | **0%** (語彙を定数化) |
| `failed_rdkit` (**私のコード**が厳格すぎ) | 15% | **0%** (valence チェックを外して再試行) |
| `failed_confseq` (**baseline の真の限界**) | 8% | **15%** |
| 書けた | 62% | **85%** |

`heavy_atom_mol` は `Chem.SanitizeMol` を厳格に呼んでいて、BioLiP のリガンド記録 +
CCD SMILES では valence が通らない分子 (金属配位を共有結合で書いたもの、
N(=O)=O の nitro 等) を落としていた。ConfSeq に必要なのは環と芳香族の認識だけ
なので、valence チェックを外して再試行するようにしたら 15% が戻った。
そのうち半分は結局 ConfSeq が書けず `failed_confseq` に移ったので、真の限界は
**15%** である。

**教訓**: 失敗を 1 つのカウンタにまとめない。24% という数字は
「相手の限界」「自分のバグ」「設定ミス」が混ざったもので、そのまま論文に
書いていたら baseline を不当に弱く見せていた。

**検証済み**: 後から完走した大きい観測パスと突き合わせた結果、
BioLiP 400 バケット (445 トークン観測) も GEOM 3 万分子 (398 観測) も
**列挙から外れるトークンは 1 つも無かった**。閉じたアルファベットという仮定は
2 つの独立な大サンプルで確認できている。


## 未決: MLM の対照をどう揃えるか (2026-09-06、ユーザ判断が要る)

コーパスを実際に作って規模を並べたら、**トークナイザと無関係な交絡**が出た。

| ソース | ProLIT | 貼り合わせ |
|---|---|---|
| BioLiP | 124,654 docs / 28.8M tok | 43,637 / 5.0M |
| GEOM | 11,606,552 / 360.8M | 約 1.4M / 約 100M |
| MLM 全体 | 14.6M / **940M** | 約 1.5M / **約 105M** |

差は 3 つの独立な原因からなる:

1. **回転 augmentation** — ProLIT は BioLiP で 2.5 倍、GEOM で 8 倍に増やしている。
   貼り合わせ側にはこれが**存在しない** (ESM3 も ConfSeq も不変なので同一文書が
   N 個できるだけ)。これは表現の性質であって手心ではない
2. **被覆率** — ConfSeq が 10-15% 落とす (BioLiP 複合体で 90%、デコイで 85%)
3. **PLINDER 511M トークンを貼り合わせ側で作っていない** (受容体の取り回しが
   別途必要で、今夜は手が回らなかった)

**このまま 105M 対 940M で比べてはいけない。** 勝っても負けてもトークナイザの
話にならない。選択肢:

- **(A) 対照を揃える (推奨)**: ProLIT 側の MLM も BioLiP+GEOM だけで、同じ
  ステップ数・同じ seed で学習し直す。既存コーパスがあるので追加の
  トークン化は不要、node_f が 1 本増えるだけ。回転 augmentation を
  **入れたまま**にするか外すかは別問題 (下記)
- **(B) 貼り合わせ側を 940M まで広げる**: PLINDER の受容体取り回し +
  ESM3 符号化 + コーパス構築。実装 1-2 日 + GPU 数時間
- **(C) 規模差を明記して比べる**: 最も安いが、査読で必ず突かれる

**回転 augmentation を対照から外すかどうか**は別の判断で、外すと ProLIT に
ハンデを課すことになる。事前登録の規則は「迷ったら baseline に有利な側を
主報告にする」なので、**外した (= document 数を揃えた) 対照を主報告とし、
入れたものを併記する**のが規則どおりだが、外した対照を作るには ProLIT 側の
コーパスを `--num-rotations 1` で作り直す必要があり、GEOM は VQ を通すので
GPU 時間がかかる。

**貼り合わせ側の MLM 学習はどの選択肢でも必要**なので先に進める。
対照の作り方だけ、起床後に決めてもらう。


## デコイコーパスの被覆率は 92.7% (2026-09-06、shard3 実測)

最初に完走したシャードで n=75,164 ポーズ:

| 理由 | 件数 | 割合 |
|---|---:|---:|
| 書けた | 69,711 | **92.7%** |
| `failed_confseq` (真の限界) | 4,533 | 6.0% |
| `failed_rdkit` (残り) | 920 | 1.2% |
| `failed_oov` | **0** | 0% |

小サンプルの 85% より良い。語彙の定数化で OOV は完全に消え、
sanitize の緩和で rdkit 起因も 1.2% まで下がった。

ProLIT の `div` デコイコーパスとの比較 (10 シャード分):

| | ProLIT | 貼り合わせ (12 シャード外挿) |
|---|---|---|
| docs | 1,423,936 (`--num-rot 2`) | 約 805,000 (回転なし) |
| tokens | 325.7M | 約 88M |
| tokens/doc | 229 | 109 |

**回転を 1 に揃えると docs はほぼ一致する** (ProLIT 712k 対 貼り合わせ 805k;
シャード数の違いを補正すると被覆率 93% と整合)。デコイ側は MLM 事前学習と違い
規模の交絡が小さいので、ヘッドの比較は素直に成立する。


## SplitWriter は殺されると索引を丸ごと失う (2026-09-06、repo 全体の潜在バグ)

GEOM ビルドの途中経過を見ていて気付いた: `train.bin` が 33.5 MB まで育って
いるのに **`train.len` が 0 バイト**だった (実読で確認、メタデータの遅延では
ない)。

原因は 2 つのストリームの伸び方の違い。1 文書はトークンを数百バイト、長さを
**きっかり 2 バイト**足す。Lustre では `open()` が `st_blksize` からバッファを
決め、それが数 MB あるので、`.bin` が何十回もフラッシュする間に `.len` は
まるごとメモリに留まる。

**walltime で殺されたコーパス構築は、トークンを全部書き終えていても
`.len` が空で、トークンを文書に切り戻せない。** コーパス構築はこの repo で
最も長いジョブで、終わり方はたいてい walltime なので、これは実害である。

`SplitWriter` に 1 MB ごとの明示フラッシュを入れた (`.len` を先に出す:
索引がトークンより長いのは読み込み時に大声で失敗するが、逆は単に短い
コーパスに見えるだけ)。50 万文書に 1 回の syscall で、殺されても使える
コーパスが買える。`tests/test_token_io_durability.py` が固定。

**走行中のジョブには効かない** (Python が既に旧コードを読んでいる)。
GEOM 4 本は 4.8 時間で tar 50.1 GB のうち 34.4 GB を読了、外挿で約 6.9 時間、
上限 8 時間なので余裕は 1 時間ほど。落ちたら `.len` を失うので作り直しになる。
